# 《别只会和 AI 聊天》书籍站设计

日期：2026-09-24  
状态：待用户复核

## 1. 目标

创建一本面向非 AI 专业读者的中文在线书，帮助产品、运营、设计、初级开发和技术管理者从“会写 Prompt”逐步理解“怎样把 AI 做成可靠的工程系统”。书籍通过 GitHub Pages 免费公开，内容可持续维护，不依赖后端服务。

本书不追求框架 API 教程，也不深入模型训练、Transformer 数学或推理优化。读者读完后应能：

- 区分 Prompt、Workflow、Agent 与多 Agent；
- 用“目标、上下文、工具、状态、循环、验证、边界”描述一个 Agent 系统；
- 判断什么时候不需要 Agent；
- 看懂一个 Agent 项目从 Demo 到上线要补哪些工程能力；
- 用一张检查表评审自己的 Agent 方案。

## 2. 读者与写作原则

### 2.1 目标读者

- 第一次系统了解 Agent 工程的人；
- 需要和 AI 工程师协作的产品、设计、运营和管理者；
- 会调用模型 API，但尚未做过生产级 Agent 的开发者。

### 2.2 表达方式

- 先讲生活类比，再给工程术语；
- 每节只解决一个核心问题；
- 每章包含一张原创示意图、一个轻松例子、一份踩坑清单和三道小测；
- 对有争议的概念明确写出“这是方便理解的模型，不是唯一标准答案”；
- 英文术语首次出现时给出中文解释，后续保留常见英文名。

幽默例子服务于理解，不嘲讽具体人群，不拿安全、隐私或生产事故开低俗玩笑。

## 3. 内容结构

全书采用“先认识、再组装、后上线”的三幕结构，共一个序章、十章和三个附录。

### 第一幕：先别急着造机器人

1. **序章：会聊天，不等于会做事**  
   用“实习生只回收到，但从不交付”的例子引出 Agent 工程。
2. **第一章：AI Native 到底 Native 在哪**  
   从“给旧产品加聊天框”到“围绕模型能力重新设计流程”。
3. **第二章：Prompt、Workflow、Agent，不是三种包装**  
   用外卖下单、婚礼流程和临场救火区分固定流程与动态决策。
4. **第三章：ReAct，一边想一边做一边看结果**  
   解释观察、行动和反馈循环，以及为什么循环必须能停。

### 第二幕：给 Agent 装上手脚和记事本

5. **第四章：工具与 MCP——会说话之后，怎么碰到真实世界**  
   讲工具契约、参数、权限和失败返回，不把 MCP 神化成“万能插座”。
6. **第五章：状态与记忆——别让它把昨天的外卖当今天的需求**  
   区分会话上下文、任务状态、长期记忆、知识库和审计记录。
7. **第六章：Loop 到 Graph——事情开始分叉时怎么办**  
   从单循环升级到有分支、重试、并行和人工确认的状态图。
8. **第七章：多 Agent——开会的人变多，不代表事情更快**  
   解释角色边界、交接协议、共享状态、冲突处理和何时坚持单 Agent。

### 第三幕：从能跑到敢上线

9. **第八章：验证与可观测性——答对一次不叫可靠**  
   讲评测集、轨迹、证据、回归、成本与延迟。
10. **第九章：失败、恢复与安全边界**  
    讲超时、重试、幂等、补偿、沙箱、最小权限和人工接管。
11. **第十章：从 Demo 到生产——一张工程检查表**  
    用完整案例串起需求、方案、实现、验证、发布和复盘。

### 附录

- 术语表：Agent、Workflow、Tool、MCP、RAG、Memory、Graph、Eval；
- 方案评审清单：适用性、可靠性、安全、成本、运营；
- 延伸阅读：公众号原文、官方工程文章和入门书目。

## 4. DeliveryAI 案例研究

DeliveryAI 只作为工程方法案例，不作为产品宣传或源码导读。公开书稿采用重新命名、重新绘图和去标识化描述。

| 可公开的抽象模式 | 对应章节 | 教学重点 |
| --- | --- | --- |
| API、UI、拨测与准入分层 | 第二章、第十章 | 不同验证层不能互相冒充 |
| 每轮任务使用唯一运行标识 | 第五章、第九章 | 状态隔离、可追踪、可清理 |
| 固定执行图与汇总节点 | 第六章 | 从线性循环升级为图 |
| 只有真实执行且证据完整才通过 | 第八章 | 评测不是一句“看起来没问题” |
| 产品失败、环境阻塞、配置错误分开 | 第八章、第九章 | 失败分类决定恢复动作 |
| 凭证隔离、写操作开关与最小权限 | 第九章 | 安全边界属于主流程，不是补丁 |

禁止公开：内部 Host、账号、产品 ID、凭证、未脱敏日志、报告、真实用户数据、私有 API 细节、未合入能力、仓库截图和未授权源码片段。

## 5. 来源与版权边界

- 微信公众号「Agent 工程实践」17 篇文章用于选题与观点梳理；书稿使用自己的结构、表述、例子和原创插图，不整段搬运原文。
- 重要观点在每章末尾列出来源链接，并区分“来源观点”“本书归纳”“案例推演”。
- 技术事实优先引用官方文档或官方工程文章，例如 Anthropic 的 agent/workflow 区分、VitePress 与 GitHub Pages 部署文档。
- 本地 DeliveryAI 仅用于抽象工程模式；任何事实若无法在允许公开的材料中再次确认，就不写成具体产品事实。

### 5.1 证据分级

每条可能影响读者判断的事实都记录来源等级和核对日期：

1. **A 级：一手权威来源**
   协议规范、官方文档、官方仓库、论文原文和项目维护者的工程文章。概念定义、接口能力和安全边界优先使用 A 级来源。
2. **B 级：可信工程实践**
   知名工程团队的生产复盘、作者署名的技术博客和正式出版书籍。用于解释取舍和补充案例。
3. **C 级：社区材料**
   教程、榜单、论坛讨论和二次解读。只用于发现线索，不能单独支撑关键结论。

核验规则：关键结论至少需要“一条 A 级来源”，或“两条相互独立的 B 级来源”；只有 C 级来源的内容不进入正文。Star 数、下载量和社交热度只反映关注度，不证明架构更正确。

### 5.2 项目学习矩阵

首版重点比较下列仍在维护的开源项目，但不做简单排名：

| 项目 | 重点学习 | 不直接推导的结论 |
| --- | --- | --- |
| LangGraph | 状态图、持久化、恢复与人工介入 | 有图就一定比简单 Workflow 好 |
| Microsoft AutoGen | 分层架构、事件驱动与多 Agent 协作 | 多 Agent 天然优于单 Agent |
| CrewAI | 角色、任务与协作编排 | 角色命名等于可靠的职责边界 |
| PydanticAI | 类型约束、依赖注入与结构化结果 | 类型检查能消除模型不确定性 |
| OpenAI Agents SDK | Agent、handoff、guardrail 与 tracing 的最小原语 | SDK 默认配置已经满足生产要求 |
| Google ADK | 代码优先的 Agent 构建与系统化评测 | 评测指标可以脱离具体任务复用 |
| Semantic Kernel | 企业集成、插件与跨语言编排 | 抽象层越多，系统越易维护 |
| Langfuse / Phoenix | 轨迹、评测和可观测性 | 有追踪页面就等于建立了质量体系 |

书中只引用项目稳定概念和公开接口，不依赖某一版本的短期语法；版本相关内容必须标注访问日期。

### 5.3 文章与书籍来源

- Anthropic《Building effective agents》：workflow / agent 区分、简单优先、环境反馈与停止条件；
- Anthropic Claude Agent SDK 工程文章：上下文收集、行动、验证和重复循环；
- Model Context Protocol 官方规范：Host、Client、Server 与 Tools、Resources、Prompts；
- OpenAI Agents SDK 官方文档：handoff、guardrail、tracing 等原语；
- Google ADK 官方评测文档：工具轨迹、响应质量和多轮评测；
- Microsoft Research AutoGen 文章：Core、AgentChat、Extensions 的分层；
- Chip Huyen《AI Engineering》及其 Agents 长文：成本、延迟、步骤数和任务成功率；
- 其他知名工程博客只在与官方资料交叉确认后采用。

仓库将维护 `sources/source-index.yml`，为每条来源记录标题、作者或机构、URL、来源等级、访问日期、适用章节和核验备注。章节末尾只展示读者需要的简洁参考，不把内部研究笔记全部倒进正文。

## 6. 站点与技术方案

### 6.1 技术栈

- VitePress：内容与页面生成；
- Markdown / Vue：章节内容与少量交互组件；
- 原生 SVG / CSS：原创架构图和流程图；
- pnpm：依赖管理；
- GitHub Actions：构建与部署；
- GitHub Pages：静态托管。

选择 VitePress 的原因是内容优先、中文搜索与移动端体验成熟、部署简单。暂不加入后端、账号、评论、埋点或 CMS。

### 6.2 信息架构

- 首页：书籍承诺、适合谁、三条阅读路线、五分钟导览；
- 章节页：左侧目录、正文、右侧页内导航；
- 案例页：DeliveryAI 脱敏案例与工程检查表；
- 术语页：按概念关系组织，不按字母机械罗列；
- 来源页：文章与官方资料链接、访问日期和用途说明。

### 6.3 视觉方向

采用“工程手册 + 轻量漫画”的风格：米白纸张底色、深墨蓝正文、荧光绿用于行动与通过、珊瑚橙用于风险与失败。插图使用清晰的节点、箭头和小人物动作，不使用泛滥的玻璃卡片、机器人头像或无意义渐变。

## 7. 内容生产与审核流

1. 从公众号、官方文档、开源仓库、工程博客和书籍中提取候选观点；
2. 按 A/B/C 证据等级登记到来源索引，关键事实完成双源核验；
3. 按章节目标重写成小白叙事；
4. 为每章制作原创图和生活化例子；
5. 执行事实、版权、公开边界、版本时效和术语一致性检查；
6. 由审判者按“事实—采纳—风险—结论”复核；
7. 通过构建、链接、移动端和可访问性检查；
8. 合并到 `main` 后由 GitHub Actions 发布。

## 8. 错误处理与降级

- 外部来源打不开：保留标题和链接，不凭印象补写原文观点；
- 搜索索引构建失败：部署失败，不发布半成品；
- 图片缺少替代文本：质量检查失败；
- 内部信息无法确认可公开：删除具体名词，改写为通用模式；
- GitHub Pages 暂时未生效：先验证 Actions 成功，再轮询公开地址，不重复推送相同提交。

## 9. 验收标准

### 内容

- 至少序章和十章，每章包含图解、例子、工程要点、踩坑清单与小测；
- 首页五分钟导览能独立讲清 Agent 工程全貌；
- DeliveryAI 案例不含内部标识与未公开能力；
- 关键事实有 A 级来源或两条独立 B 级来源，引用不冒充原创；
- 每章在来源索引中有可追溯记录，版本相关事实标注访问日期；
- 项目比较关注设计取舍，不用 Star 数或营销文案代替技术判断。

### 工程

- `pnpm build` 成功；
- 所有内部链接有效，外部链接有明确文本；
- 桌面宽度和 390px 移动端均可阅读；
- 键盘可完成导航，图片有替代文本，正文对比度满足基本可访问性；
- GitHub Actions 成功，Pages 地址返回 HTTP 200；
- 仓库不包含密钥、内部 Host、绝对路径或 DeliveryAI 源码。
