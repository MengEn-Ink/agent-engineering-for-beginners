# 案例：交付型 Agent 的质量门

这一案例来自真实工程模式的抽象与重组。我们虚构一个“交付型 Agent”：它接收业务目标，调用多个工具完成任务，再把结果交给使用者。案例只讨论通用设计，不对应任何特定公司、产品或私有系统。

## 背景：为什么“跑起来”还不够

团队最初有两类验证：接口测试能证明服务响应，浏览器脚本能证明页面可以打开。但用户真正关心的是一段完整旅程：创建任务、等待执行、处理交互、看到结果、确认资源被正确清理。

早期报告常出现一个危险句式：“脚本已启动，因此链路正常。”启动只证明起点存在，不能证明动作真的发生。于是团队把质量门改成一条证据链：预检确认环境和权限；执行器完成真实动作；每个节点写出本轮证据；聚合器只接受完整、同源、未过期的结果。

## 系统分层

案例把验证分成四层，每层只回答自己的问题：

| 层 | 回答的问题 | 不能冒充什么 |
| --- | --- | --- |
| 静态检查 | 代码、配置、契约是否自洽 | 真实环境已经可用 |
| API 旅程 | 核心业务链是否真实完成 | 用户页面体验正常 |
| UI 旅程 | 用户是否能从界面完成目标 | 内部数据一定正确 |
| 运行探针 | 系统在一段时间内是否持续可用 | 所有边界场景都覆盖 |

这条边界很重要。页面显示“准备就绪”不能当作业务已执行；单元测试全绿也不能证明外部依赖可用。每层产出自己的证据，最后由聚合器判断是否满足本次发布目标。

## 状态：每一轮都有自己的身份证

每次运行创建唯一 Run ID。测试资源名称、证据目录、节点结果和清理清单都绑定它。这样并行任务不会相互读取残留，失败后也能回答“这是谁创建的、应该由谁清理”。

运行状态至少包含：目标、环境、开始时间、当前节点、节点结果、证据路径、失败分类、清理状态。写入外部系统前记录幂等标识；恢复时先查询真实状态，避免因超时重复创建资源。

## 证据：只有执行器能写“通过”

调度器可以启动任务、收集结果，却不能替执行器补写 PASS。一个节点要通过，必须同时满足：真实动作已执行；结果状态明确；证据属于当前 Run ID；证据结构完整；时间没有早于本次运行。

如果节点没有运行、JSON 损坏、证据来自上一次、路径越界或集合不完整，聚合结果保持失败或阻塞。这叫 fail-closed。它可能让报告不那么“漂亮”，却能防止系统在最需要诚实时自我安慰。

一个实用的证据清单包括：操作目标、输入摘要、工具回执、业务状态、时间、版本和隐私脱敏说明。截图可以辅助，但不能替代可查询的业务结果。

## 失败如何被分类

同样是红灯，恢复动作可能完全不同：

| 分类 | 示例 | 下一步 |
| --- | --- | --- |
| 产品失败 | 业务返回错误、状态不符合预期 | 记录复现证据，交产品代码修复 |
| 环境阻塞 | 依赖不可用、凭证过期、容量不足 | 恢复环境后从检查点重跑 |
| 配置错误 | 目标环境、变量或参数非法 | 立即停止，修配置，不消耗执行预算 |
| 测试缺陷 | 断言错误、用例与契约漂移 | 修测试，不能归罪产品 |
| 清理失败 | 主任务完成但测试资源残留 | 单独告警并执行受限回收 |

分类应来自结构化证据，不靠日志里出现某个模糊单词。无法可靠归类时保持 UNKNOWN，并转人工复核；UNKNOWN 不能进入通过集合。

## 安全边界

交付型 Agent 通常需要读写能力，因此预检先验证目标环境、账号范围和写开关。凭证由运行环境安全注入，不进入源码、参数、日志和报告。认证信息只能发送到预先配置的目标；页面、接口响应和日志一律视为待验证数据，不能反过来修改 Agent 的系统规则。

测试数据遵循“谁创建、谁清理”：只操作带本轮标识的资源，不删除共享或未知资源。不可逆动作只能在专用环境、显式开关和人工授权同时成立时执行。

## 从影子门禁到真正阻断

新质量门先进入 shadow：运行、收集结果、暴露误报，但不影响发布。当覆盖率、稳定性、耗时和失败分类达到约定标准后，升级为 warn；再经过一段观察，才允许 block。升级依据是历史证据，不是“大家感觉差不多”。

每次规则变化都要回答：新增阻断会不会误伤？豁免在执行前还是执行后决定？如果硬门要求所有必需项 PASS，那么被合法豁免的项目应在执行前移出必需集合，而不是执行后把 BLOCKED 改名为 PASS。

## 给自己的复用清单

1. 把“脚本启动”和“业务完成”分开；
2. 每轮使用唯一标识，隔离状态、资源与证据；
3. 执行器负责事实，聚合器不能制造成功；
4. 未知、超时和缺证据默认不放行；
5. 失败分类直接连接下一步恢复动作；
6. 凭证、写权限和目标范围在执行前验证；
7. 先影子运行积累证据，再逐步增加阻断力。

## 公开边界

本案例只保留公开可复用的工程模式。它不包含内部地址、账号、产品标识、凭证、日志、报告、源代码片段、真实用户数据或尚未发布的能力。案例名称、流程和示例均经过泛化，不能用于推断任何特定系统的当前实现状态。
