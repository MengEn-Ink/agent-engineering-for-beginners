# 2026 年 9 月：六个真正影响工程实践的变化

本期只收录会改变架构边界、风险判断或运维方式的更新。日期表示发布日或本次人工核验日；所有决定截至 2026-09-25，不代表对未来版本的承诺。

## 2026-07-28 · MCP 发布新一版规范

**状态：** `revise`  
**成熟度：** evolving（有版本化规范，生态兼容仍需逐项核对）  
**影响章节：** 第 4、9 章；Agent 互操作与身份专题  
**当前决定：** 把第 4 章引用更新到 2026-07-28，补充无状态协议核心、扩展与授权演进的兼容提示；不宣称所有 SDK 已同步支持。  
**A级证据：** [source:mcp-spec] [MCP Specification 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28)

**发生了什么：** 官方规范版本向更明确的无状态核心、扩展机制和授权模型演进。版本日期是规范快照，不等于每个 Host、Client、Server 的实现版本。

**为什么重要：** 团队不能只问“支不支持 MCP”，还要记录协商版本、使用的扩展和授权假设。连接成功不等于语义兼容，更不等于权限安全。

## 2026-05-28 · A2A v1.0.1 可作为版本化互操作依据

**状态：** `adopt`  
**成熟度：** evolving（1.0 规范已发布，具体生态仍在演进）  
**影响章节：** 第 7 章；Agent 互操作与身份专题  
**当前决定：** 在前沿层介绍 A2A，不把它混入 MCP 工具调用；线上协议兼容按 `major.minor` 判断，补丁号用于文档发布追踪。  
**A级证据：** [source:a2a-spec] [A2A Specification](https://a2a-protocol.org/v1.0.1/specification/)；[source:a2a-release] [A2A v1.0.1 release](https://github.com/a2aproject/A2A/releases/tag/v1.0.1)

**发生了什么：** A2A 进入 1.0 系列，描述独立 Agent 应用之间如何发现能力、交换消息、管理任务和交付制品。

**为什么重要：** MCP 更接近“Agent 如何接工具与上下文”，A2A 更接近“一个 Agent 系统如何与另一个 Agent 系统协作”。两者可能同时出现，但信任、身份和授权仍需单独设计。

## 2026-09-25 · NIST 推进 AI Agent 标准倡议

**状态：** `watch`  
**成熟度：** frontier（倡议和研究方向，不是已完成的强制标准）  
**影响章节：** 第 7、9、10 章；互操作与安全评测专题  
**当前决定：** 把身份、授权、委托链、互操作与安全评测加入设计清单；等待具体标准或测量方法稳定后再改常青正文。  
**A级证据：** [source:nist-agentic-ai] [NIST AI Agent Standards Initiative](https://www.nist.gov/artificial-intelligence/ai-agent-standards-initiative)

**发生了什么：** NIST 把 Agent 的信任、互操作、安全和评测纳入专门标准化工作。

**为什么重要：** 未来跨组织 Agent 协作的难点不会只在消息格式，还包括“谁代表谁”“授权能否转委托”“责任如何审计”。倡议说明方向，但不能被包装成现成认证。

## 2026-09-25 · 长时 Agent 开始强调“脑与手解耦”

**状态：** `adopt`  
**成熟度：** frontier（经过生产工程实践验证，尚非通用协议）  
**影响章节：** 第 5、6、9、10 章；长时运行专题  
**当前决定：** 采用检查点、稳定任务接口、可替换模型与隔离执行环境等原则；不绑定某家托管产品的私有接口。  
**A级证据：** [source:anthropic-managed-agents] [Scaling Managed Agents](https://www.anthropic.com/engineering/managed-agents)

**发生了什么：** Anthropic 公开了 Managed Agents 的工程思路，把负责推理的模型与负责长期保存状态、运行工具和管理环境的 harness 分开。

**为什么重要：** 长任务不能只靠一个越来越长的对话。模型升级、进程重启或上下文耗尽时，任务仍要能从可验证的状态恢复。

## 2026-09-25 · Context Engineering 从提示词扩展到上下文系统

**状态：** `adopt`  
**成熟度：** evolving（方法稳定，最优阈值依模型和任务变化）  
**影响章节：** 第 3、5、8 章；Context Engineering 专题  
**当前决定：** 增加上下文预算、检索、压缩、缓存、污染隔离和失效策略；不提供跨模型通用的固定 token 百分比。
**A级证据：** [source:anthropic-context-engineering] [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

**发生了什么：** 工程讨论从“把 Prompt 写长”转向“为当前决策挑选最少而充分的上下文”。

**为什么重要：** 历史、工具定义、检索结果和中间产物都会竞争有限窗口。更多上下文可能带来噪声、陈旧事实和提示注入，而不是更高准确率。

## 2026-09-25 · Agent 可观测性语义约定仍在演进

**状态：** `watch`  
**成熟度：** frontier（部分约定为 draft 或正在迁移）  
**影响章节：** 第 8、10 章；Agent 安全评测专题  
**当前决定：** 先采用 trace、span、tool call、cost、latency、outcome 等概念模型；字段名和 exporter 绑定留在适配层，避免把草案写进长期数据契约。  
**A级证据：** [source:otel-agent-observability] [OpenTelemetry · AI Agent Observability](https://opentelemetry.io/blog/2025/ai-agent-observability/)

**发生了什么：** OpenTelemetry 社区在推动 GenAI 与 Agent 的统一可观测语义，但相关约定仍会移动和调整。

**为什么重要：** 生产系统需要跨模型和框架追踪任务结果、工具轨迹、成本与延迟；同时必须避免在 trace 中泄露 Prompt、个人数据和凭证。
