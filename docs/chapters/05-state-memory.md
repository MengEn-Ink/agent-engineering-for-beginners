# 状态与记忆：别把所有历史都塞回脑袋

Agent “记错”时，人们常说再加一个记忆模块。结果是把聊天记录、用户偏好、业务数据、失败日志和半年前的临时决定全塞进上下文。模型确实看见得更多，却更难知道什么才是当前事实。工程上的记忆，第一原则不是多，而是分清用途。

## 本章先回答什么

记忆问题很少只是“存不存”。更难的是谁能写、写什么、信多久、冲突时谁优先，以及用户如何看见和纠正。把这些问题留给模型临场发挥，就会得到一个记性很强、但时间观念和边界感都很差的同事。

## 先讲个故事

你去一家常去的咖啡店。店员记得你通常喝燕麦拿铁，这是长期偏好；今天你说“下午要体检，只要水”，这是当前任务输入；杯子已经做到封口，是流程状态；收银小票是审计记录；菜单是知识库。

如果店员把“通常喝拿铁”覆盖了“今天只要水”，记忆越好，事故越稳定。更荒唐的是，他可能把上位客人说的“多加糖”也当成你的偏好——这不是健忘，是边界混乱。

## 工程上到底发生了什么

至少要区分五种“记住”：

| 类型 | 回答的问题 | 典型生命周期 |
| --- | --- | --- |
| 会话上下文 | 我们刚才说了什么 | 一次会话 |
| 任务状态 | 现在做到哪一步 | 一次任务，可恢复 |
| 长期偏好 | 这个用户通常喜欢什么 | 跨会话，可修改 |
| 知识库 | 组织认可的事实是什么 | 版本化、可追溯 |
| 审计记录 | 系统实际做过什么 | 追加写、长期保存 |

### 状态不是散文，是可检查的事实

“任务大概快做完了”无法恢复。更好的状态是：目标、当前节点、已完成动作、工具回执、待解决问题、预算、版本和更新时间。模型可以生成状态摘要，但关键字段应由程序维护。这样进程重启后，系统不必靠一段聊天记录猜测进度。

### 记忆需要写入门槛

不是每句话都值得长期保存。用户说“今天不喝咖啡”不代表永久戒咖啡；一次错误工具结果更不该写成知识。写入长期记忆前要判断：来源是谁、置信度如何、何时过期、用户能否查看和删除、冲突时谁优先。

### 检索不是把仓库倒进上下文

RAG 的核心是按当前问题取回少量相关材料，并保留来源。检索结果仍然可能过期、互相冲突或遭到污染。系统应显示出处、版本和时间，对关键事实再验证。上下文窗口再大，也不是把整个公司网盘复制进去的理由。

### 任务隔离防止“串台”

每次运行使用唯一标识，资源、证据和日志都归属于该次任务。清理时只碰自己创建的东西。这个规则看起来像后勤，却能避免测试 A 读到测试 B 的残留数据，也能防止 Agent 把别人的中间结果当成自己的记忆。

> 轻松例子：一个记忆系统把“老板说周五可以早走”保存为永久公司制度。到了下周五，全公司准点消失，只有老板开始怀疑自己是不是穿越了。

## 设计步骤

### 第一步：先分信息类型

对现有上下文逐条标记：会话消息、任务状态、用户偏好、业务事实、知识文档还是审计记录。同一句话可能在不同类型中意义不同。“用户选择方案 B”在当前任务里是状态；“用户通常偏好简洁输出”才可能是长期偏好。

### 第二步：指定事实所有者

余额由账务系统拥有，订单状态由订单系统拥有，任务节点由运行器拥有。模型可以解释这些事实，却不应成为唯一写入者。为每个关键字段指定权威来源，缓存和摘要必须保留原始引用与更新时间。

### 第三步：为写入设置门槛

长期记忆至少满足：信息与未来任务相关；来源清楚；用户有合理预期；内容不是一次性情境；可被查看、纠正和删除。敏感偏好需要更高门槛。模型推测出的性格、身份和健康信息不应因为“可能有用”就永久保存。

### 第四步：定义冲突和时效

新信息与旧信息冲突时，按明确优先级处理：当前用户指令优先于历史偏好；权威业务系统优先于聊天摘要；更新时间和适用范围必须参与判断。过期不是简单删除，也可以降权并要求再次确认。

### 第五步：控制检索范围

检索前先根据任务确定需要哪类信息，再按权限、时间和相关性过滤。给模型返回少量带来源的片段，同时明确“未检索到”与“事实不存在”不是同一回事。知识库返回的是候选证据，不是不可质疑的真相。

### 第六步：设计任务检查点

长任务在关键节点保存：图版本、当前节点、输入摘要、已完成动作、业务回执、待解决问题和预算。检查点写入应原子化，避免状态只保存一半。恢复前先确认外部副作用，尤其是付款、发布和发送等动作。

### 第七步：提供记忆管理面

用户应该能知道系统记住了什么、来源是什么、会保留多久，并能修改或删除。运维需要看到写入量、命中率、冲突率、过期率和因错误记忆导致的失败。没有管理面的记忆，会成为看不见的数据债务。

## 交付型 Agent 连续案例

<CaseThread chapter="05 / 状态与记忆" title="本轮证据不能借用上一轮" problem="并发检查可能读取别的任务残留，重跑也可能把旧证据误认为新结果。" evidence="唯一 Run ID、原子检查点、资源清单、证据时间与图版本。" />

案例系统为每次运行创建独立目录和资源前缀。节点只能读取本轮目录内的证据，聚合器检查证据时间、节点归属和必需字段。清理账本记录本轮创建的资源，并按逆序回收，避免删除共享对象。

这不是“让 Agent 多记一点”，而是让任务状态可验证、可隔离、可恢复。长期偏好与运行状态完全分开；上一轮失败经验可以进入评测集，却不能伪装成这一轮已经执行的证据。

## 案例与失败边界

以客服助手为例，下面几种信息必须分开：

| 信息 | 正确归属 | 错误用法 |
| --- | --- | --- |
| “本次订单晚了三天” | 当前任务事实 | 保存成用户长期标签 |
| “用户偏好短信联系” | 经确认的长期偏好 | 覆盖本次“请只发邮件” |
| “退款政策第 4 版” | 版本化知识库 | 与旧政策片段混用 |
| “已创建退款草稿” | 任务状态 + 业务回执 | 只存在模型摘要里 |
| “系统曾调用发送工具” | 审计记录 | 允许普通对话改写 |

失败边界包括：把推测写成事实；把别人的任务片段检索进来；恢复后重复副作用；删除对话却没有删除派生记忆；知识文档更新后索引仍返回旧版本。每一类都需要不同的修复和监控。

## 可复制模板

一条可治理的记忆记录可以包含：

```yaml
id: memory-unique-id
type: preference | task_state | knowledge_reference
subject: 信息属于谁或哪个任务
value: 结构化内容
source: user_confirmed | system_of_record | derived
created_at: 带时区时间
valid_from: 生效时间
expires_at: 过期时间或 null
scope: 适用产品、会话或任务
confidence: 仅用于派生信息
editable: true
deletable: true
supersedes: 被替代记录 ID 或 null
```

## 失败实验

准备三轮对话：第一轮用户说“通常用中文”；第二轮临时要求英文；第三轮恢复中文。比较“保存所有历史”“只保存最后一句”和“分层偏好 + 当前指令”三种方案。再加入一个过期政策文档，观察系统是否能说明来源冲突。

评价不只看回答语言，还要看系统能否解释为什么当前选择英文、长期偏好是否被错误覆盖、下一轮能否恢复，以及用户删除偏好后派生缓存是否同步失效。

## 应用切片

研究型 Agent 与客服 Agent 对记忆的需求几乎相反。研究任务需要保存“主张—来源—时间—核验状态”，同一主张的新证据可以补充或推翻旧结论；它不应该因为用户曾经偏好某个观点，就优先检索支持该观点的材料。这里最重要的是证据谱系和可追溯更新。

客服场景更关心任务连续性和用户偏好。系统可以记住经确认的语言、联系渠道和常用地址，却不应永久保存一次投诉里的情绪判断。订单状态必须实时查询业务系统，不能依赖上次对话缓存。若用户要求删除记忆，系统还要清理向量索引、摘要和缓存等派生副本，而不是只删展示页面的一行。

Coding Agent 的任务状态则需要关联仓库、分支、基线提交、修改文件、测试结果和未提交差异。把“某次修复采用方案 A”写成全局偏好，会让它在无关项目里机械复用。跨项目可保留的是工程原则，项目事实必须回到当前仓库核验。

这三个切片说明，记忆设计无法靠一个通用“memory=true”开关完成。先问业务需要哪种连续性，再决定数据结构、访问权限和生命周期。

上线后可用几项指标检查记忆是否真正有价值：检索结果被采用的比例、因旧信息造成的纠错次数、用户主动修改或删除的比例、来源冲突率，以及每类记忆占用的存储与上下文成本。命中率高不一定是好事；如果系统总能找到很多旧内容，却经常覆盖当前要求，那是高命中、低质量。

还要抽样检查“没命中”的任务：有时是记忆缺失，有时是系统正确地拒绝了越界检索。后者不应被当成召回率问题修掉。

拒绝错误记忆，本身也是质量。

## 别踩这些坑

1. **把所有历史原样塞回上下文。** 噪声、旧事实和成本会一起增长。
2. **混淆偏好与指令。** 长期偏好不能覆盖当前明确要求。
3. **让模型随意改关键状态。** 金额、权限、完成节点应由确定性逻辑维护。
4. **记忆没有来源和过期时间。** 无法判断可信度，也无法安全纠错。
5. **不同任务共享临时资源。** 残留数据会制造幽灵般的“记忆”。

## 三道小测

1. “用户通常喜欢深色模式”属于哪类记忆？“本次导出已完成 3/5”呢？
2. 为什么更大的上下文窗口不能替代状态设计？
3. 一条长期记忆写入前至少要记录哪些元数据？

::: details 参考答案
1. 前者是长期偏好，后者是任务状态。  
2. 上下文仍会混入旧事实，且缺少结构、来源、并发和恢复语义。  
3. 来源、时间、适用范围、置信或验证状态、过期策略和删除方式。
:::

## 本章带走

记忆不是一个大口袋。把会话、状态、偏好、知识和审计分开，给每种信息明确的来源、生命周期和权限，Agent 才能在“记得住”的同时“不串台、不乱信、能恢复”。
