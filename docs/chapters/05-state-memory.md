# 状态与记忆：别把所有历史都塞回脑袋

Agent “记错”时，人们常说再加一个记忆模块。结果是把聊天记录、用户偏好、业务数据、失败日志和半年前的临时决定全塞进上下文。模型确实看见得更多，却更难知道什么才是当前事实。工程上的记忆，第一原则不是多，而是分清用途。

## 先讲个故事

你去一家常去的咖啡店。店员记得你通常喝燕麦拿铁，这是长期偏好；今天你说“下午要体检，只要水”，这是当前任务输入；杯子已经做到封口，是流程状态；收银小票是审计记录；菜单是知识库。

如果店员把“通常喝拿铁”覆盖了“今天只要水”，记忆越好，事故越稳定。更荒唐的是，他可能把上位客人说的“多加糖”也当成你的偏好——这不是健忘，是边界混乱。

## 工程上到底发生了什么

至少要区分五种“记住”：

| 类型 | 回答的问题 | 典型生命周期 |
| --- | --- | --- |
| 会话上下文 | 我们刚才说了什么 | 一次会话 |
| 任务状态 | 现在做到哪一步 | 一次任务，可恢复 |
| 长期偏好 | 这个用户通常喜欢什么 | 跨会话，可修改 |
| 知识库 | 组织认可的事实是什么 | 版本化、可追溯 |
| 审计记录 | 系统实际做过什么 | 追加写、长期保存 |

### 状态不是散文，是可检查的事实

“任务大概快做完了”无法恢复。更好的状态是：目标、当前节点、已完成动作、工具回执、待解决问题、预算、版本和更新时间。模型可以生成状态摘要，但关键字段应由程序维护。这样进程重启后，系统不必靠一段聊天记录猜测进度。

### 记忆需要写入门槛

不是每句话都值得长期保存。用户说“今天不喝咖啡”不代表永久戒咖啡；一次错误工具结果更不该写成知识。写入长期记忆前要判断：来源是谁、置信度如何、何时过期、用户能否查看和删除、冲突时谁优先。

### 检索不是把仓库倒进上下文

RAG 的核心是按当前问题取回少量相关材料，并保留来源。检索结果仍然可能过期、互相冲突或遭到污染。系统应显示出处、版本和时间，对关键事实再验证。上下文窗口再大，也不是把整个公司网盘复制进去的理由。

### 任务隔离防止“串台”

每次运行使用唯一标识，资源、证据和日志都归属于该次任务。清理时只碰自己创建的东西。这个规则看起来像后勤，却能避免测试 A 读到测试 B 的残留数据，也能防止 Agent 把别人的中间结果当成自己的记忆。

> 轻松例子：一个记忆系统把“老板说周五可以早走”保存为永久公司制度。到了下周五，全公司准点消失，只有老板开始怀疑自己是不是穿越了。

## 别踩这些坑

1. **把所有历史原样塞回上下文。** 噪声、旧事实和成本会一起增长。
2. **混淆偏好与指令。** 长期偏好不能覆盖当前明确要求。
3. **让模型随意改关键状态。** 金额、权限、完成节点应由确定性逻辑维护。
4. **记忆没有来源和过期时间。** 无法判断可信度，也无法安全纠错。
5. **不同任务共享临时资源。** 残留数据会制造幽灵般的“记忆”。

## 三道小测

1. “用户通常喜欢深色模式”属于哪类记忆？“本次导出已完成 3/5”呢？
2. 为什么更大的上下文窗口不能替代状态设计？
3. 一条长期记忆写入前至少要记录哪些元数据？

::: details 参考答案
1. 前者是长期偏好，后者是任务状态。  
2. 上下文仍会混入旧事实，且缺少结构、来源、并发和恢复语义。  
3. 来源、时间、适用范围、置信或验证状态、过期策略和删除方式。
:::

## 本章带走

记忆不是一个大口袋。把会话、状态、偏好、知识和审计分开，给每种信息明确的来源、生命周期和权限，Agent 才能在“记得住”的同时“不串台、不乱信、能恢复”。
