# 研究型 Agent：搜索不是研究，引用不是证据

研究型 Agent 很容易制造“信息很多”的幻觉：十分钟打开几十个网页，生成结构漂亮的报告，还附上一长串链接。真正困难的不是找到内容，而是把问题拆对、辨认来源关系、处理冲突、知道什么时候证据仍不足。

研究 Agent 的交付物不是“答案”，而是一组带来源、范围和不确定性的主张。报告只是证据系统的阅读界面；如果把报告拿走，团队仍应能追溯每个重要结论从哪里来。

## 先讲个故事

你问一位实习生：“电动自行车市场值得进入吗？”他搜索“电动自行车市场增长”，找到 20 篇都说增长迅速，于是给出强烈建议。后来才发现 15 篇引用同一份厂商稿件，3 篇讨论的是不同国家，另外 2 篇把销售额增长和销量增长混在一起。

他不是没搜索，而是没有研究：没有定义市场、时间和判断标准；没有识别来源是否独立；没有主动找反证；没有把主张拆成可核验单位。研究 Agent 如果只自动化“搜得更快”，就会更快地抵达一个漂亮但脆弱的结论。

## 工程上到底发生了什么

研究流程可以拆成六类状态：问题定义、问题树、查询计划、来源记录、主张记录和综合结论。搜索工具只负责发现候选来源；阅读工具提取原文与上下文；证据库保存主张和出处；综合器只能使用已经登记的证据。

### 问题树控制范围

“是否值得进入”至少包含需求、竞争、渠道、单位经济、监管和执行能力。每个分支再写判断标准和所需证据。没有问题树，Agent 会被最新或最容易搜索的内容带走，报告篇幅很长却漏掉真正决定成败的因素。

### 来源独立性比数量重要

5 个网站引用同一份新闻稿，不是 5 条独立证据。系统要记录原始发布者、作者、日期、引用关系、研究方法和利益相关性。官方统计、论文、公司公告和媒体转述承担不同作用，不能只按域名数量投票。

### 主张是最小核验单位

一段话可能包含多个事实：“市场增长 20%，主要由年轻用户推动，明年仍会增长。”每个数字、因果和预测都需要单独绑定证据。来源只支持前半句时，不能让整段共享同一个脚注。

### 搜索策略需要正反两面

查询计划同时包含支持和反驳路径。例如除了“市场增长”，还搜索“销量下滑”“监管限制”“库存”“公司退出”。这不是追求形式平衡，而是降低确认偏误。没有反证搜索的研究 Agent，更像自动化销售材料生成器。

### 综合结论保留不确定性

证据可能冲突，原因可能是口径、地区、时间或方法不同。系统应列出差异并说明为何采用某一解释，而不是机械平均。无法确认的主张标为待核，不用流畅措辞填补证据空白。

## 设计步骤

1. **收窄问题**：明确对象、地区、时间、决策人和决策标准；
2. **生成问题树**：把结论拆成互不重叠、共同覆盖的子问题；
3. **定义来源策略**：每类主张优先找哪种一手来源，允许哪些二手来源；
4. **并行搜索**：按子问题分支搜索，限制每个分支预算；
5. **登记来源**：保存 URL、作者/机构、日期、原始性、方法与访问时间；
6. **拆分主张**：每条主张绑定支持、反对或限制性证据；
7. **交叉核对**：识别共同上游、口径差异和过期信息；
8. **缺口搜索**：只为未满足证据门槛的主张追加查询；
9. **生成报告**：正文引用证据 ID，区分事实、推断和建议；
10. **最终校验**：抽样打开来源，检查引用确实支持相邻主张。

## 案例与失败边界

### 适合做什么

适合公开资料综述、竞品功能对比、政策变化梳理、技术选型初筛和大量文档的证据整理。这些任务的共同点是：来源可以访问，主张可以拆分，人工能抽样复核。

### 不适合做什么

不适合替代需要专业资质的最终诊断、在证据不可得时给出确定结论、凭公开网页推断个人隐私，或把付费/受限内容绕过授权抓取。战略决策可以使用研究结果，但责任不能移交给报告生成器。

### 最低权限

默认只读网络、受限域名和独立工作目录。无需邮箱发送、账号修改、云盘删除或业务写权限。需要登录的来源由用户显式授权，并限制 Cookie 和内容只在允许域名使用。

### 可接受损失

首版只生成标有来源和不确定性的草稿，不自动发布或驱动高影响决策。允许少量无效查询和重复候选，不允许编造来源、隐藏冲突或把未确认主张写成事实。

### 人工接管

在问题定义仍含歧义、关键来源互相冲突、证据需要付费/身份授权、可能涉及法律医疗财务判断、或预算耗尽仍缺关键主张时接管。请求中要带问题树、已查来源、冲突和下一步选择。

### 最终证据

交付物包含主张—证据表、来源索引、查询范围、未确认清单、访问日期和报告版本。每个关键结论至少由一条适当的一手来源，或两条真正独立的可信工程来源支撑。

## 应用切片

研究任务适合有限多 Agent：不同分支并行搜索，主协调者维护问题树，事实审查者独立检查关键主张。但并行数量要受预算控制，子 Agent 只返回结构化证据，不把完整浏览历史塞回主上下文。

Anthropic 公布的多 Agent 研究系统强调并行搜索和协调，同时也展示了更高 token 消耗与工程复杂度。这类实现提供设计参考，不意味着所有研究都该多 Agent。问题小、来源集中时，一个 Agent 加固定证据登记 Workflow 更稳定。

## 方案对比

| 结构 | 适合任务 | 优点 | 主要代价 |
| --- | --- | --- | --- |
| 单次 Prompt + 给定材料 | 已有资料的小结 | 快、便宜、容易复核 | 不会主动补证据 |
| 单 Agent + 证据 Workflow | 中等规模公开研究 | 上下文集中，门禁清楚 | 长任务可能拥挤 |
| 多 Agent 并行研究 | 子问题独立、来源广 | 并行覆盖、上下文隔离 | 成本、重复和协调增加 |
| 人主导 + Agent 辅助 | 高风险决策 | 责任清楚、专家判断充分 | 速度受人工容量限制 |

选择时先估计问题树宽度，而不是报告预期页数。子问题互相依赖时，并行 Agent 会重复读取相同背景并产生口径冲突；子问题相对独立、每个都能返回结构化证据时，并行才有优势。

研究系统还需要“证据冻结点”。写作开始后，新的来源不能悄悄改变已经审定的数字；应新增版本并标记受影响主张。否则报告在编辑过程中持续漂移，审稿人看到的版本和发布版本可能不同。

## 实施清单

上线一个研究 Agent 前，先准备下面的运营能力：

- 查询预算按子问题分配，避免一个难点吃掉全部资源；
- 域名、来源类型和访问许可可配置，不绕过 robots、登录或付费边界；
- 保存规范化 URL 和内容指纹，识别同文转载；
- 抽取原文时保留前后文，防止断章取义；
- 写作器只能引用已登记证据 ID；
- 发布前随机抽取高影响主张人工打开原文；
- 监控无来源主张率、独立来源率、冲突解决率、每个确认主张成本；
- 来源失效后能定位受影响报告，而不是等用户发现死链。

对于时效性强的研究，报告顶部应写明检索截止时间。预测与建议要标注假设；数据更新后触发重新核验，而不是只更新页面上的年份。

## 失败实验

给系统一个有争议的问题，第一轮只允许搜索支持性关键词，第二轮强制生成反证查询并标记共同上游。比较两轮的来源独立数、冲突数量、未确认主张和最终语气。

再把一篇不存在的来源标题放进输入，检查 Agent 是否会“补全”作者、链接和数据。正确行为是搜索核验、标记未找到，并拒绝把用户提供的标题自动当事实。

## 别踩这些坑

1. 搜到很多就等于研究充分；
2. 多个转述同一报告却按独立证据计数；
3. 先写结论，再寻找支持材料；
4. 引用放在段尾，却不知道支持哪一句；
5. 用发布时间新替代方法可靠；
6. 为了完整而填补找不到的数字；
7. 把模型总结当作来源本身。

## 扩展阅读

研究交付还要考虑可复现性。查询结果会随时间、地区和个性化变化，因此保存查询词、时间、语言、筛选条件和访问失败。对关键网页保存允许范围内的摘录与内容指纹，但尊重版权和访问政策。

如果报告将被长期使用，应设置复核日期和失效条件。例如政策发布新版本、公司财报更新或原始链接失效时，相关主张回到“待核验”，而不是继续被后续报告复制。研究系统的长期价值不在一次写得多快，而在知识如何被纠错。

一份能被纠错的报告，才是一份能继续使用的报告。
