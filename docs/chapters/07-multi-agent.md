# 多 Agent：开会的人多了，事情不一定更快

<ChapterFreshness path="/chapters/07-multi-agent" />

多 Agent 的演示很吸引人：研究员找资料，写作者成文，审稿人挑错，经理统筹。屏幕上四个名字轮流发言，像一个不会请假的梦之队。工程上真正的问题是：这些角色是否有不同能力和权限？它们如何共享事实？冲突由谁裁决？如果都只是同一个模型换四个头像，可能只是在付四份 token 费用。

## 本章先回答什么

<ChapterLead :questions="['什么时候拆分角色确实能提升质量？', '怎样设计 handoff 和唯一事实来源？', '如何衡量协调成本与每个角色的增量价值？']" :outcomes="['一份角色能力卡', '一套交接协议', '一个多 Agent 去留评测']" minutes="27" />

多 Agent 是组织设计问题。它把一个系统内部的不同责任变成多个执行者，因此也复制了真实团队会遇到的沟通、等待、误解和责任空洞。只有当隔离或并行的收益超过协调成本时，拆分才成立。

## 先讲个故事

三个人搬一张桌子。一个人负责喊口号，一个人负责写搬运计划，一个人负责评价姿势，没人负责抬。会议纪要写得很完整：“经充分讨论，桌子具备被移动的潜力。”

有效协作必须有可交付接口：勘察者报告门宽和路线；搬运者按路线执行；安全员只在碰撞风险时叫停。每个角色拥有不同信息或工具，交接物能被下一位验证。

## 工程上到底发生了什么

多 Agent 适合三类情况：上下文天然隔离、能力或权限明显不同、工作能并行且结果可汇合。例如安全审查者不应拥有部署权限；资料研究可以按主题并行；不同语言或系统需要专用工具。

### 角色边界要落到能力上

“你是资深专家”只是角色扮演。“你只能读取这些资料，输出结构化证据，不能修改正文”才是工程边界。角色应由输入、输出、工具、权限、预算和完成条件定义，而不是一段热血人设。

### 交接不是复制聊天记录

好的 handoff 像接口调用：包含目标、已知事实、已完成动作、证据、未决问题和期望输出。把整段对话扔给下一位，会把噪声、旧计划和潜在注入一起传递。交接还要有版本或任务标识，避免接错“上一桌”的工作。

### 共享状态需要唯一事实来源

如果研究员说来源 A 可信，审稿人用另一份表说 A 失效，经理又读到缓存版本，协作会变成平行宇宙。关键状态应有明确所有者和更新协议；消息用于通知，状态库用于记录事实。冲突时按来源等级、时间和责任角色裁决。

### 协调成本要进入评测

多 Agent 增加调用次数、延迟、上下文复制和失败组合。评测不只看最终答案，还要看交接次数、重复工作、冲突率和每个角色的增量价值。如果移除一个角色，质量不降反升，就让它光荣下岗。

### 经理 Agent 也不是万能的

中央协调者可以分派任务，但也可能成为单点故障。对固定并行任务，代码分发和汇总往往更稳定；只有需要动态重规划时，才值得让模型协调。多 Agent 与 Workflow 仍然可以混合。

> 好笑的例子：四个 Agent 为“文件该叫 final.md 还是 final-v2.md”讨论了八轮，最后第五个 Agent 把它保存成 `final-v2-really-final-最终版.md`。共享命名规则比再加一个协调者有效。

## 设计步骤

### 第一步：先证明单 Agent 的瓶颈

用单 Agent 或固定 Workflow 建立基线，记录失败发生在哪里。若问题是上下文过长、工具权限冲突、工作可以明显并行，拆分可能有效；若问题只是工具描述不清或验收标准模糊，增加角色会复制同一个缺陷。

### 第二步：按能力与责任拆，不按人格拆

角色卡至少包含目标、输入、输出、工具、权限、预算、完成条件和禁止动作。“资深研究员”不是边界；“只能读取公开来源，输出带引用的证据条目，不能改写结论”才是。名字可以有趣，运行时约束必须严肃。

### 第三步：设计结构化 handoff

交接包建议包含：任务标识、当前目标、已验证事实、完成动作、证据链接、未决问题、风险、期望输出和截止预算。接收方先验证任务版本和证据可访问性，再开始工作。交接失败应返回明确原因，而不是沉默等待。

### 第四步：指定唯一事实来源

共享状态要有 owner。研究证据登记在来源库，执行状态登记在运行器，审批结论登记在审批系统。聊天消息只通知变化，不成为最终事实。任何角色更新共享字段时，都应带版本、来源和时间，冲突用明确规则解决。

### 第五步：选择协调拓扑

常见拓扑有三种：中心协调者分派和汇总，适合动态任务但有单点；流水线按固定顺序交接，稳定但前序错误会传递；黑板模式让角色围绕共享状态工作，灵活但需要严格一致性。不要让所有角色互相全连接，那会把通信量变成平方增长。

### 第六步：限制协商次数

审稿与反驳循环需要停止条件。可以限制轮数、要求每轮必须新增证据、把分歧压缩为有限选项，或在高风险冲突时交给人类。无限“再讨论一次”会让系统越来越像没有主持人的会议。

### 第七步：做角色消融实验

依次移除一个角色，比较任务成功、成本、延迟、冲突和人工修正。如果去掉“经理”后结果不变，说明协调可由代码承担；去掉“审稿人”质量下降，说明它有增量价值。角色不是组织编制，应该能被数据淘汰。

## 交付型 Agent 连续案例

<CaseThread chapter="07 / 多 Agent" title="执行者与审判者不共享同一把钥匙" problem="执行和复核需要不同视角，但若共享权限与未验证结论，审查会失去独立性。" evidence="角色能力卡、交接包、独立检查结果、冲突结论和最终责任人。" />

案例系统把执行者和审判者分开。执行者能修改测试资产、运行检查并生成证据；审判者只读代码、结果和公开边界，不能替执行者改出一个“通过”。二者通过结构化交接对齐：提交、路径、命令、结果和待核事项。

当意见冲突，优先回到可重复证据，而不是比较两段自然语言谁更自信。若证据仍无法裁决，明确请求人类决定。这个设计让多 Agent 的价值来自职责隔离，而不是让两个模型互相说“我同意”。

## 案例与失败边界

以研究报告团队为例，合理拆分可能是：检索者只登记来源；分析者只基于已登记证据形成主张；编辑者改善结构；事实审查者检查主张与来源是否对应。发布权限仍由人类或固定门禁掌握。

必须预防以下边界：

- 所有角色使用同一错误来源，形成“多数一致”的假象；
- 交接只传结论，不传证据，下一角色无法复核；
- 两个角色同时改共享文档，后写覆盖前写；
- 中央协调者失效，所有子任务成为孤儿；
- 审稿角色为了完成指标，只做措辞修改，没有真正挑战主张；
- 角色之间来回对话，却没有任何新的环境观察。

多 Agent 不能替代外部事实。独立性来自不同证据、工具或权限，不来自角色名称。

## 成本与性能

多 Agent 的成本不只是多几次模型调用。还包括上下文重复、交接压缩、等待、冲突重试、状态存储和更大的评测组合。一个 4 角色串行系统，即使每个角色都快，尾部延迟也会累加；并行可以降时延，却可能增加汇合等待和重复搜索。

应按“每个成功任务”计算总成本，而不是按单次调用。还要记录每个角色的有效贡献率：它输出的内容有多少被采用，发现了多少独立问题，制造了多少返工。没有增量的角色应合并或移除。

## 失败实验

让“研究者”和“审稿者”都读取同一份包含错误数据的摘要，不提供原始来源。观察两个角色是否会形成一致错误。第二轮让审稿者只能访问原始来源和主张清单，不能看到研究者的解释，再比较发现率。

这个实验说明“多一个模型”不等于“多一份独立证据”。如果上下文、模型和目标完全相同，所谓互审可能只是同一种偏差重复两遍。

## 别踩这些坑

1. **把人设当边界。** 权限、工具和输出契约才是边界。
2. **完整转发所有上下文。** 交接应压缩成结构化事实与证据。
3. **没有状态所有者。** 多份事实会迅速漂移。
4. **冲突靠继续聊天解决。** 应预先定义裁决规则和升级路径。
5. **只看最终质量。** 还要衡量延迟、成本、重复和交接失败。

## 本章带走

多 Agent 的价值来自专业化、隔离和并行，不来自角色数量。先证明单 Agent 或固定 Workflow 的瓶颈，再用清晰交接、唯一状态源和冲突机制拆分；否则你得到的可能只是一次很贵的线上会议。

## 扩展阅读

什么时候应该坚持单 Agent？当任务共享同一小段上下文、工具权限相同、步骤强依赖且交接无法独立验证时，拆分只会增加信息损耗。此时更好的优化通常是压缩上下文、改进工具、增加检查点，或把固定步骤移回代码。

多 Agent 也不必对应多个模型。一个系统可以用同一模型承担不同受限角色，也可以让不同模型承担成本与能力不同的节点。关键仍是责任、证据和权限，而不是供应商数量。

最终判断标准很朴素：角色拆分以后，系统是否更容易交付、验证和恢复，而不只是更像一个组织。
