# 客服与运营 Agent：会说人话，更要守业务边界

客服是最容易让 Agent 显得聪明的场景，也是最容易把错误变成承诺的场景。模型可以理解口语、总结上下文、匹配知识并生成自然回复；一旦连接订单、退款、优惠和消息工具，它说的每句话都可能推动真实业务。

客服 Agent 的成熟度不由“像不像真人”决定，而由解决率、政策正确率、动作准确率、接管质量和用户损失共同决定。一个语气温柔却承诺错误赔付的系统，比一个措辞普通但边界清楚的系统更危险。

## 先讲个故事

用户说：“包裹又没到，我明天就要送人，你们到底行不行？”一个只做文本生成的机器人回复：“非常理解您的心情，我们一定为您妥善解决。”听起来体贴，却没有查订单、没有确认时间、也没有任何解决动作。

另一个 Agent 先识别订单，查询物流，发现地址异常；它说明事实，提供修改地址或退款草稿两个选项。用户选择退款后，系统检查资格、生成草稿，金额超过自动范围，于是带着订单、政策和建议转给人工。用户不必重新讲故事，人工也不必重新查资料。

## 工程上到底发生了什么

服务任务可以分为四层：理解、知识、决策和执行。理解负责识别意图、对象和情绪；知识层检索政策与产品资料；决策层判断流程和风险；执行层调用真实业务工具。把四层混在一个 Prompt 里，会让模型既当政策库、又当审批人、又当收银员。

### 知识回答与业务事实分开

“退货政策是什么”来自版本化知识库；“这笔订单是否符合退货条件”需要实时业务数据和确定性规则。模型可以解释规则，却不能只根据用户描述推断订单状态。回答里应区分政策、当前事实和下一动作。

### 情绪识别不是给用户贴标签

情绪只用于当前对话的服务策略，例如优先回应损失、减少重复追问、尽快升级。不要把“愤怒”“难缠”永久写入用户画像，也不要让情绪评分决定基本权益。模型可能误读讽刺、方言和文化表达。

### 解决率必须带政策正确率

如果 KPI 只有“是否让用户停止对话”，Agent 可能通过过度承诺、错误补偿或快速转人工刷高指标。应同时看首次解决、政策符合、业务动作正确、用户重复联系、接管率和投诉后果。

### 人工接管是连续服务

接管包包含用户目标、身份与订单、已确认事实、查过的知识版本、已执行动作、准备动作、风险和用户情绪摘要。人工能一眼接续，而不是要求用户第四次提供订单号。接管后 Agent 停止自动写操作，等待明确恢复。

## 设计步骤

1. **按意图分级**：信息咨询、状态查询、草稿动作、高影响动作、投诉与安全事件；
2. **绑定权威来源**：政策来自版本化知识库，订单来自实时业务系统；
3. **设计澄清**：只问影响决策的最少问题，能从系统读取的不再问用户；
4. **限定工具**：查询、草稿、提交、通知拆开，风险逐级提高；
5. **建立政策门**：金额、时限、身份和例外由确定性规则校验；
6. **处理情绪**：先承认具体损失，再提供可执行选项，不做空泛保证；
7. **定义升级**：高金额、政策冲突、法律威胁、身份不清、连续失败进入人工；
8. **验证动作**：以订单和资金状态为准，不以回复文本为准；
9. **评测全链路**：从首次输入到问题解决或高质量接管。

## 案例与失败边界

### 适合做什么

适合高频政策问答、订单状态查询、材料收集、标准流程引导、回复草稿、低风险标签与路由。输入和业务对象可识别、政策可查询、结果可验证时，价值最清楚。

### 不适合做什么

不适合在身份不明时披露账户信息，不适合绕过政策直接承诺赔偿，不适合单独处理法律、医疗、安全威胁或高价值争议，也不适合用情绪推断长期用户价值。

### 最低权限

默认只读用户可见范围内的订单和知识；写权限从创建草稿开始。提交退款、改地址、发外部消息分别需要明确权限、白名单、额度和审计。不同租户数据严格隔离。

### 可接受损失

允许回答需要人工修正、草稿被拒绝或低风险路由不够精准；不允许泄露他人订单、越权退款、虚构政策、重复扣款或对外做无法兑现的承诺。

### 人工接管

身份校验失败、政策冲突、用户明确要求人工、同一问题连续失败、高风险金额、潜在人身安全或法律事项时立即接管。接管请求显示已确认事实和已执行动作，不附带未经验证的模型猜测。

### 最终证据

信息咨询以引用的政策版本和回答摘要为证；业务动作以对象 ID、前后状态、金额、批准和回执为证；接管以队列 ID、负责人、上下文包和服务时限为证。

## 应用切片

运营 Agent 与客服共享许多能力，却有不同风险。运营更常批量处理内容、名单和通知，因此需要预览受众、抽样内容、频率限制、去重和撤回方案。一个单用户回复错误影响有限，一次群发错误可能同时影响大量人。

适合的混合结构是：模型生成候选和解释，Workflow 固定审批与发布，规则系统控制名单、频次和敏感边界。数据分析可以生成异常线索，但指标定义和统计口径必须来自确定性代码。

## 方案对比

| 服务模式 | 自动化范围 | 适合阶段 | 关键门禁 |
| --- | --- | --- | --- |
| 知识助手 | 查政策、生成回复 | 数据与流程尚未打通 | 引用版本、隐私范围 |
| 流程导航 | 查询状态、收集材料 | 主流程稳定 | 身份、字段完整性 |
| 动作草稿 | 创建退款/通知草稿 | 工具有可靠回执 | 政策、金额、预览 |
| 有限自动 | 白名单低风险动作 | 已有稳定评测与运营 | 额度、幂等、抽检 |

不要直接从知识问答跳到有限自动。每一层都要积累真实失败：知识助手先证明不会编造政策；流程导航证明能识别对象；动作草稿证明参数和回执可靠；最后才讨论有限自动。

同一系统可以按意图处于不同层级。查询物流可能有限自动，地址修改只生成草稿，高额赔付始终人工。权限不是产品级总开关，而是“意图 × 风险 × 用户范围”的组合。

## 实施清单

- 为每条政策保存版本、生效范围和 owner；
- 身份校验前不查询或展示个人订单；
- 意图分类低置信时先澄清，不猜业务对象；
- 回复中的数字、时限和承诺来自结构化字段；
- 工具调用前展示目标和影响，调用后核对真实状态；
- 用户要求人工时不设置劝退循环；
- 接管队列监控等待时间和上下文完整率；
- 将重复联系、错误承诺和误退款纳入质量指标；
- 批量运营动作先小样本预演，再逐步扩大；
- 任何自动策略都有关闭开关和回滚路径。

运营负责人还要定期查看“系统没有回答”的问题。高频未知可能表示知识缺口，高频权限阻塞可能表示流程设计不合理，高频人工接管可能是风险策略过严，也可能是系统正确保护了用户。数据需要结合案例解释。

## 失败实验

准备 30 个客服样本，其中包含同名用户、过期政策、金额边界、重复请求、强烈情绪和明确要求人工。比较两个版本：一个只优化回复满意度，一个同时校验政策和业务状态。观察哪一个更容易过度承诺。

再模拟退款接口成功但回执超时。检查系统是否按幂等键查询，而不是再次退款。把接管包交给不了解前情的人工，记录其理解任务所需时间和需要重新询问的字段。

## 别踩这些坑

1. 用漂亮话代替真实动作；
2. 把知识答案当当前订单事实；
3. 让模型自由决定金额和资格；
4. 为提高解决率压低人工接管；
5. 把一次情绪永久写入画像；
6. 群发前不预览受众和数量；
7. 接管只传聊天全文，不传结构化事实。

## 扩展阅读

多语言客服还要区分翻译质量与政策质量。模型可以把回复翻译得自然，但货币、日期、时区、地址和法规适用范围必须结构化处理。翻译后的承诺要与原政策字段对照，不能因为语言更礼貌就改变责任。

对话摘要也要有更新规则。每次用户纠正事实，摘要应标记旧字段被替代；人工接管后，人的最终处置成为权威结果。系统不能在下一轮继续引用接管前的错误建议。摘要压缩要保留对象、时间、金额、用户选择和未决事项，删除重复寒暄。

服务运营的另一个风险是指标诱导。如果团队只追求自动解决率，Agent 会减少接管；只追求平均时长，它会过早结束；只追求满意度，它可能过度补偿。指标需要成组设计，并对高风险错误设置硬门。

最后，给用户明确退出自动服务的渠道。能随时转人工、看到系统正在查询还是准备动作、知道数据用途，会显著提高信任。隐藏 Agent 的限制并不会让体验更智能，只会让错误更突然。

还要把渠道差异写进设计。网页聊天可以展示按钮和进度，邮件回复间隔长且容易丢失上下文，电话转写可能有姓名和数字错误，群聊又涉及多位参与者与隐私。相同意图在不同渠道需要不同的确认方式、超时和证据，不能只复用一段 Prompt。

服务知识更新时，先在影子流量上检查新旧答案差异，再扩大范围。紧急政策可以优先上线确定性规则，避免等待整个知识索引完成重建。
