# 从 Demo 到生产：一张工程路线图

<ChapterFreshness item-id="chapter-10-production" />

Demo 的任务是证明“有可能”；生产系统的任务是证明“每天都能在边界内完成”。二者都重要，却不能互相冒充。一个 Demo 可以手动准备完美输入、忽略偶发失败；生产系统要面对脏数据、权限变化、模型升级、网络抖动和用户突然改主意。

## 本章先回答什么

生产化不是给原型增加一个部署脚本，而是建立持续承诺：输入变化时仍能工作，失败时知道发生了什么，高风险时能停下，版本变化后有办法证明没有退化。

## 先讲个故事

学校科技节上，一辆小车沿黑线跑完十米，掌声雷动。把它放到城市里送外卖，马上遇到红绿灯、雨水、施工、没电、顾客改地址和保安不让进。不是小车“退化”了，而是世界终于出现了。

Agent 从 Demo 到生产，就是不断把被演示隐藏的世界补回来：真实入口、工具边界、状态、证据、失败、恢复、成本和运营。

## 工程上到底发生了什么

可以按七个关口推进，而不是一次追求全自动：

### 1. 写清交付物

把“帮助用户解决问题”改成可检查结果，例如“生成一份来源完整的调研草稿，并标出无法确认的结论”。同时写出禁止结果，如“不自动外发、不编造来源”。

### 2. 建立最小基线

先用一次 Prompt 或固定 Workflow 完成最窄场景，记录成功率、人工耗时、延迟和成本。没有基线，就无法证明 Agent 化带来提升。

### 3. 设计工具与状态

给每个工具明确输入、输出、副作用和权限；把任务状态从聊天文本中抽出来；每次运行有唯一标识；写操作可幂等、可查询或可补偿。

### 4. 加入反馈循环

让系统每次行动后读取真实结果，判断是否更接近目标。只有固定流程无法覆盖的节点，才交给模型动态选择。设置停止条件和人类检查点。

### 5. 建立证据与评测

定义任务结果、关键轨迹、业务回执和不可违反的规则。用真实失败补充回归集，记录版本、步骤、费用、延迟和失败分类。未执行、未知或缺证据都不算通过。

### 6. 分阶段放权

先只读，再生成草稿；先影子运行，再提示风险；指标稳定后才让门禁真正阻断或允许写入。权限范围和损失上限随证据逐步扩大，而不是首日“全自动驾驶”。

### 7. 运营与复盘

上线不是结束。要监控质量漂移、工具错误、人工接管、成本和延迟；为模型、Prompt、工具和图版本保留变更记录；事故后更新评测集和恢复手册。

### 一个小而完整的发布门

发布前至少回答：目标环境是否正确？凭证是否就绪？测试数据是否隔离？用例是否真的执行？证据是否属于本轮？失败是否分类？资源是否清理？只有这些答案都可核对，系统才有资格说“通过”。

> 反例：团队把演示视频命名为 `production-final-final.mp4`，然后认为文件名里的 production 已经完成了上线准备。文件名很坚定，系统没有。

## 设计步骤

### 第一步：确定服务边界和 owner

列出支持的用户、任务、输入范围和明确不支持的情况。每个工具、数据源、评测集、告警和人工队列都要有负责人。Agent 失败不是一个单一团队的问题：模型质量、业务规则、工具依赖和运营接管通常属于不同 owner。

### 第二步：定义 SLO 与质量预算

除了可用性，还要定义任务成功率、证据完整率、p95 延迟、单任务成本、人工接管率和高风险误操作上限。不同任务采用不同目标：生成草稿可以容忍更多人工修正，自动更新权限则需要更严格门槛。

SLO 不是发布后才统计的仪表盘数字。它决定模型选择、超时、并发、缓存、降级和是否值得自动化。

### 第三步：建立版本与变更面

一次运行要能关联模型、系统提示、工具 schema、知识版本、图版本和代码提交。任何一项变化都可能改变结果。发布说明应写出改了什么、预期影响哪些任务、用什么评测验证、如何回滚。

### 第四步：用两条独立轴线推进

上线成熟度至少有两个维度，不能排成一条混合阶梯。

第一条是**门禁执法强度**：`shadow → warn → block`。shadow 只记录“如果启用会怎么判”；warn 对异常发出提醒但不阻断；block 才真正阻止不满足要求的发布。它回答的是“质量结论影响发布到什么程度”。

第二条是**Agent 执行权限**：`read-only → draft → approval-required → limited-auto`。只读只能收集事实；draft 可以产生可撤销草稿；approval-required 在高影响动作前等人批准；limited-auto 只对满足白名单、额度和可逆性条件的动作自动执行。它回答的是“Agent 能对真实世界做多少事”。

两条轴可以独立推进。一个只读诊断 Agent 的质量门可以已经 block；一个 limited-auto 执行 Agent 的新评测规则仍可处于 shadow。任何升级都要有数据标准和观察窗口。失败率下降但人工接管暴涨，不一定是改进；平均延迟下降但尾部任务经常超时，也不能扩大范围。

| | read-only | draft | approval-required | limited-auto |
| --- | --- | --- | --- | --- |
| shadow | 记录结论 | 记录草稿 | 模拟批准请求 | 只模拟动作 |
| warn | 异常告警 | 草稿告警 | 批准前告警 | 自动动作后告警 |
| block | 证据不足即拦截 | 草稿不合格即拦截 | 未批准绝不执行 | 越出白名单即拦截 |

### 第五步：把门禁放在正确位置

开发门禁检查代码、契约和离线评测；发布门禁检查目标环境、凭证、数据隔离和真实旅程；运行门禁持续看 SLO、异常和容量。三者不能互相冒充。单元测试通过不能证明外部系统可用，线上一次通过也不能替代回归。

### 第六步：设计降级和回滚

模型不可用时可退回固定 Workflow，写工具不可用时可生成草稿，搜索失败时可返回已知来源和缺口。回滚不仅是部署旧代码，还要处理运行中的任务、已写状态、缓存、索引和审批请求。

### 第七步：建立运营节奏

每日看失败类别和严重异常，每周看质量、成本、时延和接管趋势，每次事故补回归样本，每次工具或模型升级跑对应集合。定期删除无效规则、过时记忆和长期不用的图分支，避免系统只增不减。

## 交付型 Agent 连续案例

<CaseThread chapter="10 / 生产化" title="从影子结论到真正阻断" problem="新门禁一开始不够稳定，直接阻断会误伤发布，不阻断又无法证明价值。" evidence="阶段目标、历史运行、误报/漏报、证据完整率、耗时、owner 和回滚条件。" />

案例系统先让新门禁以 shadow 运行，只记录如果启用会做出的决定。团队核对误报、失败分类和证据缺口；稳定后进入 warn，异常会通知但不阻断；达到事先约定的覆盖与稳定标准后，才把必需节点设为 block。

阶段变化写入版本化配置，不能由运行中的 Agent 自行放宽。遇到紧急豁免，先明确对象、期限、原因和批准人，再从必需集合中移除；不允许把执行后的 BLOCKED 改成 PASS。

## 案例与失败边界

生产化最容易低估的不是模型，而是周边系统：

- 身份登录过期导致工具全部失败，却被统计为模型能力下降；
- 上游字段改名，模型仍生成合理文字，但写入对象错位；
- 模型版本升级改善平均质量，却让少数高风险任务退化；
- 评测集长期不更新，分数稳定但真实用户问题已经变化；
- 人工接管队列没有容量，系统能“升级处理”却没人接；
- 成本告警只看单次调用，忽略循环重试后的任务总成本。

每类失败应有可观察信号、owner、恢复动作和用户沟通。不能把所有问题归为“AI 偶发不稳定”，那会让真正可修的工程缺陷长期存在。

## 成本与性能

生产成本包括模型 token、工具调用、搜索、存储、追踪、人工审核和失败重跑。优化时看每个成功任务的总成本，而不是某一步单价。可以通过缓存稳定上下文、缩小检索范围、让小模型处理分类、把固定节点移回代码、并行独立分支来优化。

延迟要看用户感知路径。长任务可以流式展示状态和证据，但不要用动画假装进展；阶段无输出需要超时。后台任务完成后通知用户，前台交互则优先快速确认目标和风险。优化不能牺牲证据和安全门。

## 失败实验

在预发布环境模拟四类故障：模型超时、工具限流、身份过期、写操作成功但回执丢失。检查系统能否正确分类、保存检查点、避免重复副作用、触发对应 owner，并向用户返回可行动信息。

再执行一次模型升级对照。不要只比较最终答案，检查工具选择、步骤数、成本、尾部延迟和高风险样本。若平均分提高但权限错误增加，升级应停止。

## 别踩这些坑

1. **把 Demo 成功率直接当生产成功率。** 真实世界的输入和故障分布不同。
2. **没有基线就上复杂架构。** 无法知道增加的成本换来了什么。
3. **一次性开放所有写权限。** 应随证据分阶段放权。
4. **只监控模型报错。** 业务未完成、证据缺失和成本异常也需要告警。
5. **把发布当终点。** 模型、数据和工具都会变化，需要持续回归。

## 三道小测

1. 为什么先建立简单基线，再引入 Agent？
2. “影子运行”解决什么问题？
3. 发布门里为什么“未执行”不能等同于“未发现失败”？

::: details 参考答案
1. 基线提供质量、成本与效率的比较对象，避免复杂度无法证明价值。  
2. 它让新系统在不影响真实决策的情况下积累证据和暴露失败。  
3. 没有执行就没有证据；缺少失败记录不能证明成功。
:::

## 本章带走

从 Demo 到生产，不是把同一段代码放到更大的服务器，而是补齐目标、工具、状态、验证、安全、恢复和运营。最成熟的 Agent 系统往往看起来不神秘：该固定的固定，该动态的动态，每一步都有证据，出错时知道停在哪里。

## 扩展阅读

生产成熟度的最后一项是“可退出”。如果一个 Agent 功能停止维护，团队能否关闭新任务、完成或转移运行中任务、撤销凭证、保留必要审计并恢复旧流程？退出方案能检验系统是否真正理解自己的状态和依赖。

把退役也写进生命周期，可以避免一次成功的试验变成多年无人负责的影子服务。
