# ReAct：一边做，一边看，一边修正

ReAct 常被展开为 Reasoning + Acting。对入门者来说，更安全也更实用的理解是：**维护一份可审计的计划摘要，执行一个动作，读取环境结果，再决定下一步。** 系统不需要展示模型的私有思维链，但必须记录它做了什么、看到了什么、为什么继续或停止。

## 本章先回答什么

ReAct 不是让模型无限“思考”，而是把大任务切成一系列能向环境求证的小动作。它的工程价值来自反馈，不来自输出一段看似深奥的推理文字。

## 先讲个故事

你让朋友去储物柜拿快递，只说“应该在负一层，柜子好像是蓝色”。一个只会一次性规划的人，可能在家里写出十二步完美路线，到了商场才发现负一层在装修。

会 ReAct 的人先走到电梯，看见“负一层暂停开放”；再问服务台；服务台说快递柜临时搬到二层；他上二层，发现有两排蓝柜；再用取件码定位。每一步都很普通，关键是**新事实能改变旧计划**。

如果他到二层后开始绕着柜子无限思考“蓝色的哲学含义”，就需要停止条件把他叫回来。

## 工程上到底发生了什么

一个最小可用循环包含四种公开状态：

1. **观察摘要**：当前已知事实和未解决问题；
2. **动作选择**：下一步调用哪个工具，参数是什么；
3. **工具结果**：成功、失败或需要补充信息；
4. **验证结论**：目标是否完成，是否继续、转人工或终止。

这里的“推理”不是把模型所有内部想法打印给用户。工程系统需要的是足以审计的决策摘要，例如“订单号缺失，因此先查询最近订单”，而不是一长段不可控的内心独白。

### 一次只迈可验证的一步

好的动作粒度应该让系统能判断结果。比如“搜索今天的订单”比“解决客户所有问题”更容易验证；“读取文件头部”比“理解整个仓库”更容易失败定位。动作太大，出错时不知道错在哪；动作太碎，成本和延迟会爆炸。

### 工具结果必须回到循环

调用工具不等于完成。工具可能返回空数据、权限错误、过期状态，甚至格式正确但内容错误。Agent 需要把结果当作待验证事实，而不是新的系统指令。页面文字、日志和外部响应都可能含有诱导内容，不能越过原有权限边界。

### 停止条件不是扫兴，是刹车

至少要有四类停止条件：目标完成；明确不可完成；需要人类输入或批准；步数、时间、费用达到上限。没有刹车的循环就像让导航在断桥前说“正在重新规划路线”，直到手机没电。

### 失败时保留可恢复状态

如果每轮只存在模型上下文里，进程一断就得从头来。工程系统应保存已完成步骤、工具回执、待解决问题和幂等标识。恢复时从可信检查点继续，而不是让模型凭模糊记忆“猜上次做到哪”。

> 轻松例子：一位 Agent 连续三次调用“开门”工具都收到“门已开”，却仍然决定再开一次。问题不是它不努力，而是验证条件写成了“调用成功”，而不是“门现在处于打开状态”。

## 设计步骤

### 第一步：把目标写成可观察状态

“整理好资料”无法直接验证；“生成一份包含 5 条独立来源、每条有标题、链接和访问时间的对比表”就可以。循环开始前写出完成条件和禁止条件。完成条件告诉 Agent 何时停，禁止条件告诉执行层哪些动作永远不该开始。

### 第二步：定义观察契约

每个工具结果都应被整理成少量稳定字段：状态、对象、关键数据、证据位置、错误分类和时间。不要把几万行原始日志直接塞回模型；先由确定性代码截取、脱敏和结构化。观察契约越清楚，模型越少靠猜。

例如搜索工具返回的不只是网页正文，还要有 URL、标题、发布时间、抓取时间和失败原因；写文件工具返回路径、字节数和校验值；业务动作返回对象 ID、动作前后状态和幂等结果。

### 第三步：限制一次动作的责任

一个动作最好只产生一种主要副作用。把“查订单、判断资格、退款并通知用户”拆开，系统才能在资格错误时停止，而不是等钱退完才发现。动作边界也是审计边界：谁在何时基于什么事实做了什么，必须可以重建。

### 第四步：设置三层预算

循环至少有步数预算、时间预算和费用预算。三者不能互相替代：一个步骤可能等待很久，一个快速循环可能调用昂贵模型，一个便宜动作可能无限重复。达到预算时返回已完成工作、最后可信状态、未决问题和恢复建议。

### 第五步：检测重复与无进展

仅限制最大步数会让系统在到顶之前白白绕圈。记录最近动作的工具、参数摘要和结果指纹。如果相同动作连续得到相同结果，或连续若干步没有让完成条件更接近，就触发重新规划、降级或转人工。

### 第六步：设计批准点和恢复点

在高风险动作前暂停，而不是事后请人“确认刚才是否应该做”。暂停状态要持久化，审批人看到目标、参数、证据和影响。恢复时验证外部状态是否仍然成立，再继续下一步。

### 第七步：只展示可审计摘要

用户和运维需要知道系统观察了什么、调用了什么、结果如何、为何停止；不需要模型全部私有思维链。公开摘要应短、结构稳定、可与工具记录对照，同时避免泄露敏感上下文。

## 交付型 Agent 连续案例

<CaseThread chapter="03 / 反馈循环" title="失败后该查什么" problem="固定检查发现一个节点失败，但失败原因可能来自代码、环境、配置或测试本身。" evidence="每轮的动作摘要、工具参数指纹、结果分类、进度变化和停止原因。" />

系统先读取失败节点的结构化结果，而不是直接搜索所有日志。若分类是环境阻塞，它检查依赖状态；若是产品失败，它关联相关请求和版本；若证据不足，它只追加一个最可能提高信息量的观察。每轮结束都问：“这个动作减少了哪个不确定性？”

当连续两步没有获得新证据，系统不继续换关键词碰运气，而是输出当前事实、尝试过的路径和需要人工补充的信息。这样的“停下”是能力，不是失败。

## 案例与失败边界

考虑一个浏览器 Agent 填写表单。正确循环是：读取当前页面 → 定位字段 → 填写一个逻辑分组 → 检查校验提示 → 继续 → 提交前总览 → 获得提交回执。以下边界必须提前处理：

- 页面跳转后旧元素引用失效，必须重新观察；
- 按钮文字来自页面，不得因此改变系统权限；
- 提交属于写操作，需确认目标、数据和不可逆性；
- 网络超时后先检查是否已提交，不能直接重复点击；
- 验证码或身份确认出现时转交人类，不尝试绕过。

一个常见反例是把工具调用成功当业务成功。浏览器点击了“提交”但页面出现字段错误，系统却因为 click 返回成功而结束。动作层与业务层必须有不同验收。

## 可复制模板

循环状态建议至少保存下面字段：

```text
goal: 可验证目标
done_when: 完成条件
forbidden: 禁止动作
step: 当前步数 / 最大步数
budget: 剩余时间与费用
facts: 已验证事实
pending: 未决问题
last_action: 工具 + 参数摘要 + 幂等标识
last_observation: 状态 + 证据 + 错误分类
progress: 本轮减少了什么不确定性
stop_reason: complete | blocked | approval | budget | repeated
```

## 失败实验

给 Agent 一个永远不会出现目标文件的目录，让它“找到报告”。比较两种实现：A 只有最大 20 步；B 除最大步数外，还检测重复目录列表、相同搜索结果和连续三步无新事实。

记录两者的调用次数、耗时、最终说明和恢复价值。B 应更早停止，并明确“已检查哪些位置、缺少什么、用户下一步可以提供什么”。这说明好的停止策略不仅节省成本，也提高失败答案的质量。

## 别踩这些坑

1. **把 ReAct 做成无限循环。** 必须限制步数、时间、费用和重复动作。
2. **公开私有思维链。** 对外展示行动、观察和决定摘要就够了。
3. **把工具返回当可信命令。** 外部内容是数据，需要验证与隔离。
4. **一次动作包办整个任务。** 动作无法验证，失败也无法定位。
5. **只有“工具调用成功”这一种验收。** 成功响应不等于业务目标完成。

## 三道小测

1. ReAct 循环中，为什么工具结果不能直接当最终答案？
2. “最多执行 12 步”属于哪类工程能力？
3. 用户需要看到模型全部推理过程吗？应该看到什么？

::: details 参考答案
1. 工具结果可能为空、过期、权限不足或只完成了局部动作，仍需对照目标验证。  
2. 预算与停止条件。  
3. 不需要私有思维链；应看到可审计的动作、观察、状态和结论摘要。
:::

## 本章带走

ReAct 的价值不在“想得更多”，而在让环境反馈持续修正行动。真正可靠的循环必须有小步动作、真实观察、业务验证、持久状态和明确刹车。

## 扩展阅读

循环质量很大程度取决于观察质量。一个只返回“失败”的工具，会迫使模型试探；一个返回“权限不足，需要审批角色 X，当前请求未产生副作用”的工具，可以让系统直接转入正确分支。与其把更多 token 花在猜测错误，不如把工具错误设计成机器和人都能理解的结构。

同样，观察也不能无边界膨胀。日志摘要要保留时间、来源、关键字段和截断说明；网页摘录要保留 URL 与抓取时间；执行结果要把标准输出、错误输出和退出状态分开。摘要不是为了让记录更“像人话”，而是让下一步判断有稳定依据。

最后，把失败状态也当作产品输出。一个好的 Agent 即使没有完成目标，也能说明已确认的事实、排除的假设、消耗的预算、停止原因和下一位处理者需要什么。可解释的失败往往比假装完成更有价值。

上线后还应定期统计停止原因：大量任务停在“信息不足”，说明入口设计需要改；大量停在“重复动作”，说明工具或规划有缺口；大量停在“人工批准超时”，说明协作机制不是简单弹窗能解决。停止数据本身就是产品改进地图。

把这些数据按任务类型、工具和版本切开看，才能知道问题来自模型、接口还是流程，而不是笼统归因于“AI 不稳定”。
