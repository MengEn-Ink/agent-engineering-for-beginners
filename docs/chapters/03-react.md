# ReAct：一边做，一边看，一边修正

ReAct 常被展开为 Reasoning + Acting。对入门者来说，更安全也更实用的理解是：**维护一份可审计的计划摘要，执行一个动作，读取环境结果，再决定下一步。** 系统不需要展示模型的私有思维链，但必须记录它做了什么、看到了什么、为什么继续或停止。

## 先讲个故事

你让朋友去储物柜拿快递，只说“应该在负一层，柜子好像是蓝色”。一个只会一次性规划的人，可能在家里写出十二步完美路线，到了商场才发现负一层在装修。

会 ReAct 的人先走到电梯，看见“负一层暂停开放”；再问服务台；服务台说快递柜临时搬到二层；他上二层，发现有两排蓝柜；再用取件码定位。每一步都很普通，关键是**新事实能改变旧计划**。

如果他到二层后开始绕着柜子无限思考“蓝色的哲学含义”，就需要停止条件把他叫回来。

## 工程上到底发生了什么

一个最小可用循环包含四种公开状态：

1. **观察摘要**：当前已知事实和未解决问题；
2. **动作选择**：下一步调用哪个工具，参数是什么；
3. **工具结果**：成功、失败或需要补充信息；
4. **验证结论**：目标是否完成，是否继续、转人工或终止。

这里的“推理”不是把模型所有内部想法打印给用户。工程系统需要的是足以审计的决策摘要，例如“订单号缺失，因此先查询最近订单”，而不是一长段不可控的内心独白。

### 一次只迈可验证的一步

好的动作粒度应该让系统能判断结果。比如“搜索今天的订单”比“解决客户所有问题”更容易验证；“读取文件头部”比“理解整个仓库”更容易失败定位。动作太大，出错时不知道错在哪；动作太碎，成本和延迟会爆炸。

### 工具结果必须回到循环

调用工具不等于完成。工具可能返回空数据、权限错误、过期状态，甚至格式正确但内容错误。Agent 需要把结果当作待验证事实，而不是新的系统指令。页面文字、日志和外部响应都可能含有诱导内容，不能越过原有权限边界。

### 停止条件不是扫兴，是刹车

至少要有四类停止条件：目标完成；明确不可完成；需要人类输入或批准；步数、时间、费用达到上限。没有刹车的循环就像让导航在断桥前说“正在重新规划路线”，直到手机没电。

### 失败时保留可恢复状态

如果每轮只存在模型上下文里，进程一断就得从头来。工程系统应保存已完成步骤、工具回执、待解决问题和幂等标识。恢复时从可信检查点继续，而不是让模型凭模糊记忆“猜上次做到哪”。

> 轻松例子：一位 Agent 连续三次调用“开门”工具都收到“门已开”，却仍然决定再开一次。问题不是它不努力，而是验证条件写成了“调用成功”，而不是“门现在处于打开状态”。

## 别踩这些坑

1. **把 ReAct 做成无限循环。** 必须限制步数、时间、费用和重复动作。
2. **公开私有思维链。** 对外展示行动、观察和决定摘要就够了。
3. **把工具返回当可信命令。** 外部内容是数据，需要验证与隔离。
4. **一次动作包办整个任务。** 动作无法验证，失败也无法定位。
5. **只有“工具调用成功”这一种验收。** 成功响应不等于业务目标完成。

## 三道小测

1. ReAct 循环中，为什么工具结果不能直接当最终答案？
2. “最多执行 12 步”属于哪类工程能力？
3. 用户需要看到模型全部推理过程吗？应该看到什么？

::: details 参考答案
1. 工具结果可能为空、过期、权限不足或只完成了局部动作，仍需对照目标验证。  
2. 预算与停止条件。  
3. 不需要私有思维链；应看到可审计的动作、观察、状态和结论摘要。
:::

## 本章带走

ReAct 的价值不在“想得更多”，而在让环境反馈持续修正行动。真正可靠的循环必须有小步动作、真实观察、业务验证、持久状态和明确刹车。
