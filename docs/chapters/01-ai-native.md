# AI Native 到底 Native 在哪

“AI Native”听起来像一张很贵的贴纸：把它贴在产品首页，估值仿佛就能多一个零。可工程上真正有意义的 Native，不在宣传词，而在**系统是不是围绕模型的不确定能力重新设计**。

## 本章先回答什么

读这一章时，先暂时忘掉模型型号。我们关注的是工作方式：信息怎样进入系统，谁做判断，谁执行动作，谁验证结果，发生损失时谁负责。只要这条链没变，“AI Native”往往只是入口换了皮肤。

## 先讲个故事

一家餐厅买来一位会说一百种语言的机器人，把它摆在收银台。客人说“少辣，不要香菜，赶时间”，机器人翻译得字正腔圆，然后把纸条放在桌上。厨房没收到，收银系统没记录，骑手也不知道赶时间。老板却宣布：“我们已经 AI Native 了。”

这其实只是“旧流程 + 一个聊天入口”。真正的 AI Native 餐厅会重新设计整条链路：机器人把自然语言拆成订单字段；不确定“少辣”对应几级时主动确认；把赶时间写进状态；出餐前校验过敏原；异常时把订单交给店员。AI 不再是一张嘴，而是流程里一个可观察、可约束的参与者。

## 工程上到底发生了什么

传统软件擅长确定规则：点击按钮，调用接口，得到可预测结果。模型擅长处理模糊输入：理解意图、归纳材料、生成候选方案。AI Native 的关键，是让二者各做擅长的事，而不是让模型接管一切。

可以用三层变化判断一个产品是否真的在重构：

### 第一层：界面变化

用户从点菜单变成说需求。这能降低操作门槛，但底层流程没变，仍然只是“自然语言遥控器”。价值真实，却还谈不上系统重构。

### 第二层：流程变化

模型开始参与拆任务、选工具、处理非结构化信息；确定性代码负责权限、金额、状态写入和格式校验。此时产品从“人操作每一步”变成“人给目标，系统推进流程”。

### 第三层：责任变化

系统明确哪些决定可以自动做，哪些必须有人批准；每一步留下可核对的结果；失败能恢复或升级处理。此时 AI 才进入真正的生产责任链。

一个实用判断是：**拿掉聊天框以后，系统的工作方式有没有变化？** 如果没有，可能只是 AI-enabled；如果目标表达、任务分解、工具编排、验证和人工接管都被重新设计，才更接近 AI Native。

> 好笑但真实的例子：给打印机加语音，说“请别卡纸”，不叫智能办公；让系统在打印前发现纸张尺寸不匹配、暂停任务并告诉你换哪一盒纸，才算流程被重新设计。

### 先从最简单的闭环开始

AI Native 不等于“自治程度拉满”。Anthropic 的工程建议强调：先用简单 Prompt 和评测解决问题，只有当固定流程不足时，再引入更多动态决策。越自由的系统，越需要环境反馈、停止条件和人类检查点。自由不是免费的，它会变成测试、权限和运营成本。

## 设计步骤

### 第一步：画出今天的工作，而不是明天的机器人

先选一个具体任务，把当前流程画成“触发 → 输入 → 判断 → 动作 → 结果 → 异常”。不要先写“打造智能助手”，那不是任务，只是一种愿望。比如报销场景可以写成：员工提交票据，系统识别字段，规则校验额度，负责人批准，财务付款，结果回写。

在每个节点标出当前耗时、错误和人工判断。模型最适合处理的通常是那些输入模糊、规则难以穷举、但结果可被检查的节点，例如票据分类和缺失材料说明。金额上限、付款账户、审批权限则属于确定性边界。

### 第二步：把“会做”拆成“允许做”

能力回答模型是否可能完成，权限回答系统是否应该让它完成。给每个动作标风险：只读、可逆写入、高影响写入、不可逆动作。只读搜索可以自动；创建报销草稿可以自动但保留撤销；付款必须在明确批准后执行；删除审计记录应直接禁止。

这一步会迫使团队讨论可接受损失。所谓自治程度，不是一个从 0 到 100 的炫酷滑杆，而是每个动作有不同的信任半径。

### 第三步：明确模型与代码的边界

模型负责理解模糊意图、生成候选和比较方案；代码负责身份、权限、金额、状态写入、格式、幂等和审计。一个简单判断是：如果这个条件写错会造成确定性损失，就尽量不要只把它放在自然语言 Prompt 里。

例如“判断用户是否在抱怨”可以由模型完成；“退款是否超过 500 元”应该由代码完成；“高价值客户是否需要更温和的表达”可以由模型给建议，但不能越过业务政策。

### 第四步：为每个动作设计反馈

系统调用工具后，要得到足以判断下一步的结果：成功还是失败、影响了哪个对象、业务状态是什么、有没有可核对回执。只有 HTTP 200 不够，因为接口成功不代表业务目标完成。AI Native 的闭环不是“模型说完了”，而是“环境证明变了”。

### 第五步：设计不确定时的出口

系统至少要区分信息不足、权限不足、工具失败、风险过高和目标冲突。每一类都要有下一步：追问用户、转人工、稍后重试、降级为草稿或明确拒绝。不能把所有异常都回复成“抱歉，请稍后再试”，那只是把工程问题重新塞回用户。

### 第六步：用小样本证明价值

先选择高频、低风险、反馈快的 20–50 个真实样本，比较改造前后的完成率、人工时间、错误类型、费用和用户等待。只有当新闭环持续优于旧流程，再扩大权限和范围。

## 交付型 Agent 连续案例

<CaseThread chapter="01 / AI Native" title="从回答需求到交付结果" problem="旧系统能解释如何完成任务，却不会保存状态、调用工具或验证结果。" evidence="一份从用户目标到业务回执的责任链，以及每个自动动作的权限等级。" />

在贯穿全书的案例里，用户说“帮我执行一次发布前检查”。旧版本输出一份检查建议；新版先解析目标版本和环境，运行只读预检，生成需要执行的检查图，遇到写操作先请求批准，最后返回真实结果和证据链接。

注意，这里最关键的升级不是“Prompt 写得更像专家”，而是系统获得了受限工具、持久状态和验收门。模型仍然可能判断错误，但错误被限制在可观察、可停止的路径上。

## 案例与失败边界

把三个常见产品放到同一张责任表里：

| 场景 | 模型适合做 | 硬边界 | 最终证据 |
| --- | --- | --- | --- |
| 报销助手 | 提取字段、解释缺失材料 | 额度、账户、审批链 | 草稿 ID、规则结果、审批状态 |
| 运营内容助手 | 归纳素材、生成候选 | 发布权限、敏感词、版权 | 审核记录、发布回执 |
| 故障排查助手 | 归纳日志、提出下一检查 | 生产写操作、凭证、网络范围 | 命令结果、指标变化、人工确认 |

失败边界也要提前写出。模型把“建议退款”理解成“立即退款”，如果工具允许直接打款，系统会把语义误差放大成真实损失；如果工具只允许创建草稿并要求审批，同一个模型错误会变成可发现的待办。好的架构不假设模型永不犯错，而是假设错误一定会来，并控制它能走多远。

## 可复制模板

用下面的 AI Native 改造画布评审一个流程：

| 项目 | 要填写的内容 |
| --- | --- |
| 用户目标 | 用户真正想拿到的结果，而不是想看的页面 |
| 当前流程 | 触发、输入、判断、动作、结果、异常 |
| 模型优势节点 | 模糊理解、生成、比较、规划中的哪一项 |
| 确定性节点 | 权限、金额、状态、格式、审计 |
| 工具与副作用 | 每个动作的范围、可逆性和回执 |
| 不确定出口 | 追问、重试、降级、拒绝、转人工 |
| 成功证据 | 业务状态、质量阈值、成本、时延 |
| 扩权条件 | 达到什么数据后，允许做得更多 |

## 失败实验

做一个反向实验：只在旧产品首页增加聊天框，不改变后端状态和权限。让 10 位用户用自然语言完成一个跨三步的任务，记录他们在第几步被迫回到旧界面、重复输入了什么、AI 承诺了哪些无法执行的动作。

这个实验通常会揭示两类“AI 洗白”：第一类是聊天框只做帮助中心搜索；第二类是模型生成了正确建议，却没有任何可靠方式推进业务状态。它们可以有价值，但应该被准确称为对话入口或智能辅助，而不是完整 Agent。

## 别踩这些坑

1. **把模型当成新名字。** Agent 是模型、上下文、工具、状态、控制流和验证共同组成的系统。
2. **把聊天框当成终点。** 用户想要的是事情完成，不是获得一段“听起来会完成”的文字。
3. **一上来追求全自动。** 先让高频、低风险、可验证的环节自动化；高风险决定保留人工确认。
4. **只设计成功路径。** AI Native 的差异常常出现在信息缺失、工具失败和权限不足时。
5. **用“更聪明的模型”掩盖接口问题。** 工具说明含糊、状态混乱、验证缺失，再强的模型也会被工程地基绊倒。

## 三道小测

1. 一个旧报销系统增加“帮我填报销单”的聊天框，但最终仍要用户逐项点击确认，它属于哪一层变化？
2. 为什么“模型能做”不等于“系统可以让它自动做”？
3. 如果只能先补一个能力，你会选更长的 Prompt，还是可验证的结果回执？为什么？

::: details 参考答案
1. 主要是界面变化；除非系统真正参与字段提取、校验、状态推进和异常处理。  
2. 生产系统还要考虑权限、损失上限、可逆性、证据和责任。  
3. 通常先补结果回执。没有反馈闭环，长 Prompt 只会让错误解释得更有文采。
:::

## 本章带走

AI Native 不是“多用一点 AI”，而是把模型当作不确定性组件，和确定性代码、工具、状态、验证与人类共同组成新流程。下一章，我们用一把最重要的尺子继续判断：这个任务应该是 Prompt、Workflow，还是 Agent？

## 扩展阅读

判断成熟度时，不要只看系统能自主运行多久。一个能连续运行 2 小时、却无法解释做过什么的 Agent，未必比一个每 5 分钟请求确认、但证据完整的 Workflow 更成熟。更有用的成熟度维度包括：目标是否可测、动作是否受限、状态是否可恢复、结果是否可追溯、异常是否有所有者、权限是否随证据逐步扩大。

因此，AI Native 的终点也不是“彻底无人”。优秀系统会重新安排人的位置：人不再重复搬运信息，而是在定义目标、批准高风险动作、处理真正模糊的例外和改进规则上发挥作用。自动化减少的是机械劳动，不是责任。
