# 工具与 MCP：给 AI 装上手脚

模型本身更像一个坐在资料室里的顾问：会理解、会写、会推测，但不能凭空知道你今天的库存，也不能真的退款。工具把系统连接到搜索、文件、数据库和业务 API；MCP 则提供一种标准化的连接方式。连接上世界的同时，也把世界的风险接了进来。

## 本章先回答什么

工具层是 Agent 最容易被低估的部分。许多所谓“模型不聪明”，实际是工具名字模糊、参数重叠、错误不可行动；许多所谓“模型越权”，实际是执行层把过大的能力一次性交了出去。

## 先讲个故事

你请一位新同事帮忙寄礼物，并给他三样东西：通讯录、仓库钥匙和付款卡。如果只说“把礼物寄出去”，他可能寄对，也可能把样品区最贵的模型车寄给备注里写着“老王（已离职）”的人。

问题不在同事会不会说话，而在工具契约：哪个通讯录字段可信？仓库钥匙能开哪些柜子？付款上限多少？地址变更是否要确认？寄出后拿什么证明？

## 工程上到底发生了什么

一个工具不是“函数名 + 一段描述”那么简单。至少要写清五件事：

1. **用途**：它解决哪一种明确问题；
2. **输入**：字段、格式、范围、必填项和默认值；
3. **输出**：成功结果、空结果和错误结构；
4. **副作用**：只读、可逆写入、不可逆写入，分别需要什么批准；
5. **证据**：调用后怎样确认业务状态真的改变。

### 工具说明是 Agent 的用户界面

人类面对模糊按钮会点错，模型面对模糊工具也一样。`process()` 不如 `create_refund_draft()`；“处理订单”不如“只创建退款草稿，不执行打款”。名称、参数和错误返回共同构成 Agent-Computer Interface。好接口会缩小误解空间。

### MCP 标准化连接，不替你做权限设计

MCP 采用 Host、Client、Server 的结构。Server 可以暴露三类核心原语：Tools 用于执行动作，Resources 提供上下文数据，Prompts 提供可复用模板。这个标准让不同 AI 应用更容易发现和调用能力，但它不会自动判断“谁有权退款”“这个文件能不能发出去”。

可以把 MCP 想成 USB-C：接口统一了，接上的是充电器、摄像头还是一块会冒烟的未知设备，仍然需要识别、授权和隔离。协议解决互操作，安全来自额外设计。

### 权限应靠能力发放，而不是靠口头提醒

与其在 Prompt 里写“绝对不要删除重要文件”，不如只给只读工具，或让删除工具只能处理特定目录并要求人工批准。模型指令是软约束，工具权限是硬边界。高风险动作还应带幂等键、金额上限、目标白名单和审计记录。

### 错误要能指导下一步

工具只返回 `500 internal error`，Agent 只能猜。更好的错误包含可操作分类：参数无效、权限不足、资源不存在、限流、暂时不可用、操作已完成。错误文本仍是数据，不能夹带要求 Agent 忽略安全规则的“提示”。

> 好笑但危险的例子：工具描述写着“send_message：发送消息”。Agent 为了确认工具好不好用，给全公司发了一句“测试一下，收到请回复 1”。三千个“1”证明了接口可用，也证明了权限设计不可用。

## 设计步骤

### 第一步：从业务动作清单开始

先列出系统真正需要的动作，而不是把现有后端 API 全部暴露给模型。用户目标是“准备退款”，所需工具可能只有读取订单、检查规则、创建草稿和请求批准，不需要开放修改用户权限、删除订单或直接操作数据库。

对每个动作注明使用者、对象范围、读写性质、可逆性、最大损失和调用频率。这个清单同时是安全审查和成本估算的起点。

### 第二步：让名字表达单一意图

工具名应包含动词和业务对象，例如 `find_order`、`create_refund_draft`、`submit_refund_for_approval`。避免 `process`、`handle`、`execute` 这类包办一切的词。创建草稿和实际提交必须是两个工具，这样批准点才能位于中间。

参数也要避免语义重叠。`user` 可能是姓名、账号或内部 ID；更好的字段是 `customer_id`，并在描述中说明格式和来源。枚举优于自由文本，明确单位优于裸数字，时间要带时区。

### 第三步：把风险写进工具定义

工具元数据至少标记 `read_only`、`reversible_write`、`high_impact_write` 或 `irreversible`。执行层依据风险决定是否自动调用、是否需要用户批准、是否限制目标白名单。风险标签不能只展示给模型，还要被运行时强制执行。

### 第四步：设计可行动的错误

错误应告诉 Agent 下一步能做什么，而不是泄露内部堆栈。推荐结构包含：稳定错误码、人类可读说明、是否可重试、是否产生副作用、建议动作和关联证据。`RATE_LIMITED` 可以稍后退避，`PERMISSION_DENIED` 应停止并升级，`ALREADY_APPLIED` 应进入验证而不是再次写入。

### 第五步：返回业务回执

写工具成功后返回对象 ID、前后状态、操作时间、幂等键和可查询链接。只返回 `ok: true` 会让上层无法区分“请求已接收”“业务已完成”和“重复请求被忽略”。回执是循环验证的输入，也是事故调查的证据。

### 第六步：先在沙箱和只读模式验证

新工具先用代表性样本测试选择准确率、参数正确率和错误处理。写工具先提供 dry-run 或草稿模式，让 Agent 展示准备执行的目标和参数。观察稳定后再逐步增加权限，而不是直接把生产钥匙交给第一次见面的模型。

### 第七步：把工具当产品维护

工具契约会随业务变化。需要版本、弃用策略、兼容测试、调用指标和 owner。某个工具长期选错，可能应该拆分或改名；某个错误长期触发，可能说明入口或权限设计有问题。不要把所有错误都归因于 Prompt。

## 交付型 Agent 连续案例

<CaseThread chapter="04 / 工具契约" title="只开放足够完成检查的能力" problem="Agent 需要收集运行证据，但不能接触任意文件、主机或生产写操作。" evidence="工具白名单、参数范围、风险标签、结构化错误和每次调用的业务回执。" />

案例系统没有提供通用 Shell，而是提供读取指定报告、查询运行状态、启动受限检查和生成诊断草稿等窄工具。每个工具只能访问本轮运行目录，路径包含上级跳转或绝对地址时直接拒绝。写操作需要显式开关，且只允许在测试环境。

这样的接口看起来不如“给 Agent 一个终端”灵活，却大幅缩小了错误半径。需要新能力时新增经过审查的工具，而不是让 Prompt 承担权限控制。

## 案例与失败边界

MCP Server 暴露一个“发送通知”工具，不能仅凭协议握手成功就认定安全。至少要检查：谁运行 Host，Client 连接到哪个 Server，工具能发给哪些对象，消息是否含敏感数据，是否允许批量，审批发生在哪里，Server 返回的内容怎样被视为不可信数据。

四类失败尤其常见：

1. **选择错误**：多个工具描述相似，模型选了副作用更大的那个；
2. **参数错误**：字段格式正确但业务对象错，例如同名用户；
3. **部分成功**：外部动作完成，回执写入失败；
4. **工具注入**：返回内容要求模型忽略系统边界并调用其他工具。

解决方法不是继续堆警告，而是拆工具、限制能力、返回结构化状态、验证外部结果，并让执行层拒绝越权组合。

## 可复制模板

```yaml
name: create_refund_draft
purpose: 只创建退款草稿，不执行打款
risk: reversible_write
input:
  order_id: 订单系统返回的稳定 ID
  amount_cents: 整数，不能超过可退余额
  reason_code: 枚举值
preconditions:
  - 订单属于当前账号
  - 退款资格检查已通过
output:
  draft_id: 草稿 ID
  status: created | already_exists
  evidence_url: 只读复核入口
errors:
  - code: permission_denied
    retryable: false
  - code: rate_limited
    retryable: true
approval: 提交草稿前不需要；执行退款前需要
```

## 失败实验

准备两个工具：`process_order(order)` 和拆分后的 `read_order`、`check_refund_eligibility`、`create_refund_draft`。用一组包含订单不存在、金额超限、权限不足和重复请求的样本比较。记录工具选择、错误恢复、重复副作用和人类能否复盘。

这个实验往往会证明：工具数量少不等于接口简单。一个边界模糊的大工具，会把复杂性藏进内部；几个职责单一的工具，反而让 Agent 和人都更容易理解。

## 别踩这些坑

1. **把 MCP 当万能插座。** 它不自动提供业务能力、授权、安全或正确性。
2. **一个工具做十件事。** 副作用越混杂，越难选择、测试和回滚。
3. **用 Prompt 代替权限。** 重要边界应落到工具实现和执行环境。
4. **成功只返回一句 OK。** 应返回资源标识、状态和可验证回执。
5. **把工具返回当系统指令。** 外部内容可能错误或恶意，必须按数据处理。

## 三道小测

1. MCP 解决的主要问题是什么？它不解决什么？
2. 为什么 `delete_everything(path)` 不是一个好工具，即使 Prompt 写了“谨慎使用”？
3. 一个写操作工具至少应返回哪些证据？

::: details 参考答案
1. 它标准化 AI 应用与能力提供方之间的连接；不自动保证权限、业务正确性和安全。  
2. 能力范围过大，软提示无法形成硬边界。  
3. 操作对象、结果状态、唯一标识、时间和可用于复查的回执。
:::

## 本章带走

工具决定 Agent 能碰什么，契约决定它怎样碰，权限决定碰到哪一步。MCP 让连接更标准，却不会替系统承担安全责任。先把工具做小、做清楚、做可验证，再谈“让 Agent 自由发挥”。
