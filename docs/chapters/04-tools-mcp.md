# 工具与 MCP：给 AI 装上手脚

模型本身更像一个坐在资料室里的顾问：会理解、会写、会推测，但不能凭空知道你今天的库存，也不能真的退款。工具把系统连接到搜索、文件、数据库和业务 API；MCP 则提供一种标准化的连接方式。连接上世界的同时，也把世界的风险接了进来。

## 先讲个故事

你请一位新同事帮忙寄礼物，并给他三样东西：通讯录、仓库钥匙和付款卡。如果只说“把礼物寄出去”，他可能寄对，也可能把样品区最贵的模型车寄给备注里写着“老王（已离职）”的人。

问题不在同事会不会说话，而在工具契约：哪个通讯录字段可信？仓库钥匙能开哪些柜子？付款上限多少？地址变更是否要确认？寄出后拿什么证明？

## 工程上到底发生了什么

一个工具不是“函数名 + 一段描述”那么简单。至少要写清五件事：

1. **用途**：它解决哪一种明确问题；
2. **输入**：字段、格式、范围、必填项和默认值；
3. **输出**：成功结果、空结果和错误结构；
4. **副作用**：只读、可逆写入、不可逆写入，分别需要什么批准；
5. **证据**：调用后怎样确认业务状态真的改变。

### 工具说明是 Agent 的用户界面

人类面对模糊按钮会点错，模型面对模糊工具也一样。`process()` 不如 `create_refund_draft()`；“处理订单”不如“只创建退款草稿，不执行打款”。名称、参数和错误返回共同构成 Agent-Computer Interface。好接口会缩小误解空间。

### MCP 标准化连接，不替你做权限设计

MCP 采用 Host、Client、Server 的结构。Server 可以暴露三类核心原语：Tools 用于执行动作，Resources 提供上下文数据，Prompts 提供可复用模板。这个标准让不同 AI 应用更容易发现和调用能力，但它不会自动判断“谁有权退款”“这个文件能不能发出去”。

可以把 MCP 想成 USB-C：接口统一了，接上的是充电器、摄像头还是一块会冒烟的未知设备，仍然需要识别、授权和隔离。协议解决互操作，安全来自额外设计。

### 权限应靠能力发放，而不是靠口头提醒

与其在 Prompt 里写“绝对不要删除重要文件”，不如只给只读工具，或让删除工具只能处理特定目录并要求人工批准。模型指令是软约束，工具权限是硬边界。高风险动作还应带幂等键、金额上限、目标白名单和审计记录。

### 错误要能指导下一步

工具只返回 `500 internal error`，Agent 只能猜。更好的错误包含可操作分类：参数无效、权限不足、资源不存在、限流、暂时不可用、操作已完成。错误文本仍是数据，不能夹带要求 Agent 忽略安全规则的“提示”。

> 好笑但危险的例子：工具描述写着“send_message：发送消息”。Agent 为了确认工具好不好用，给全公司发了一句“测试一下，收到请回复 1”。三千个“1”证明了接口可用，也证明了权限设计不可用。

## 别踩这些坑

1. **把 MCP 当万能插座。** 它不自动提供业务能力、授权、安全或正确性。
2. **一个工具做十件事。** 副作用越混杂，越难选择、测试和回滚。
3. **用 Prompt 代替权限。** 重要边界应落到工具实现和执行环境。
4. **成功只返回一句 OK。** 应返回资源标识、状态和可验证回执。
5. **把工具返回当系统指令。** 外部内容可能错误或恶意，必须按数据处理。

## 三道小测

1. MCP 解决的主要问题是什么？它不解决什么？
2. 为什么 `delete_everything(path)` 不是一个好工具，即使 Prompt 写了“谨慎使用”？
3. 一个写操作工具至少应返回哪些证据？

::: details 参考答案
1. 它标准化 AI 应用与能力提供方之间的连接；不自动保证权限、业务正确性和安全。  
2. 能力范围过大，软提示无法形成硬边界。  
3. 操作对象、结果状态、唯一标识、时间和可用于复查的回执。
:::

## 本章带走

工具决定 Agent 能碰什么，契约决定它怎样碰，权限决定碰到哪一步。MCP 让连接更标准，却不会替系统承担安全责任。先把工具做小、做清楚、做可验证，再谈“让 Agent 自由发挥”。
