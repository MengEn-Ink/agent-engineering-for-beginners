# Coding Agent：会写代码，不等于会完成工程任务

代码生成是 Coding Agent 最显眼的能力，却不是最难的部分。真实任务要求它找到正确仓库和分支，理解现有约束，复现问题，修改最小范围，运行有效测试，保留用户改动，解释风险，并把结果交付到可审查的提交或 PR。

Coding Agent 的环境比聊天复杂：仓库里有多层说明、生成文件、未提交改动、不同语言工具链和隐藏依赖。它必须先认识现场，再动手。

## 先讲个故事

你请一位聪明维修工修漏水。他进门看见水迹，立刻把墙刷白，说“问题已修复”。代码生成也可能这样：修改了报错附近的一行，让一个测试变绿，却没有找到真正漏点；或者在错误分支改了正确代码。

可靠的维修工先确认是哪套房、哪个阀门、漏水如何复现、墙内管路怎么走；修完后开水测试，再检查其他房间是否受影响。Coding Agent 的工程链同样是探索、计划、失败测试、最小修改、回归和差异审查。

## 工程上到底发生了什么

Coding Agent 同时操作三种状态：代码状态、执行状态和协作状态。代码状态包括分支、提交和工作树；执行状态包括命令、测试和构建；协作状态包括需求、评审意见和不允许覆盖的用户修改。

### 仓库说明是局部规则系统

项目根目录和子目录可能有不同约束：语言版本、测试命令、禁止修改区域、命名和提交规则。在支持分层规则的 Coding Agent 中，应从工作目录向目标文件逐层读取，距离文件更近的规则可以补充或收紧上层规则；其他工具则以各自公开的规则加载机制为准。不能凭跨项目经验覆盖当前仓库事实。

### 探索要回答“改哪里”，不是尽可能多读

先用文件清单、搜索和调用关系缩小范围，再读直接相关代码、测试和文档。大量无目标读取会挤占上下文，也更容易把旧实现当需求。探索结果应形成一个短计划：根因假设、目标文件、验证方法和不碰的范围。

### 测试先证明缺陷

修 bug 前写一个会因当前行为失败的测试，确认它因为目标缺陷而红，不是因为环境或语法。然后做最小修改让它绿，再运行相关回归。测试写在代码之后立即通过，无法证明它真的捕获过问题。

### 差异是最终产品的一部分

完成前检查 `git diff`、未跟踪文件和生成物，确认没有密钥、日志、截图或无关格式化。报告必须区分“我改了什么”“我验证了什么”“环境限制导致什么没验证”。不要把命令成功等同于需求完成。

## 设计步骤

1. **确认现场**：路径、仓库、分支、HEAD、工作树、语言和包管理器；
2. **读取规则**：项目说明、目标目录约束、构建和测试入口；
3. **复现问题**：用最小命令获得稳定失败，记录真实错误；
4. **定位根因**：搜索调用路径、数据来源和现有相似实现；
5. **写失败测试**：先红，且失败原因与缺陷一致；
6. **最小实现**：限制改动范围，复用现有模式；
7. **验证分层**：目标测试、相关包、静态检查、生产构建；
8. **审查差异**：敏感信息、用户改动、生成物和不变量；
9. **交付**：提交、PR 或补丁，附命令和风险；
10. **上线观察**：将真实失败加入回归，而不是只补说明。

## 案例与失败边界

### 适合做什么

适合边界清楚的缺陷修复、小型功能、测试补充、文档同步、机械迁移和可在本地验证的重构。仓库规则明确、反馈快、差异可审查时成功率更高。

### 不适合做什么

不适合在需求责任不清时自行决定重大产品行为，不适合未经授权修改生产数据、密钥、访问策略或不可逆基础设施，也不适合把“测试无法运行”包装成完成。

### 最低权限

默认只访问目标仓库和必要依赖；写权限限制在工作分支或 worktree；网络按需开放；生产凭证不进入环境；推送、合并、发布和删除需要明确授权。读取 `.env` 不是调试的默认动作。

### 可接受损失

允许局部实现失败、测试红和需要返工；不允许覆盖用户未提交改动、强推历史、泄露凭证、向错误仓库推送或在未验证时声称通过。任何自动提交都应可回退且范围清楚。

### 人工接管

需求存在多种业务解释、需要新增外部权限、涉及数据迁移、测试环境长期不可用、发现疑似凭证泄露、或改动超出最初模块时接管。请求应附根因证据、可选方案、影响范围和已完成验证。

### 最终证据

交付包包含仓库与提交、变更文件、关键差异、红绿测试记录、构建结果、未验证项、风险和回滚方式。PR 页面只是载体，证据必须能从命令和代码重现。

## 交付型 Agent 连续案例

在书中的案例里，Coding Agent 不直接修改业务服务，而是在独立测试仓库补端到端能力。它先核对当前分支和真实实现位置，再为测试数据创建唯一 Run ID；发现页面 500 时先捕获网络响应，拿到后端错误证据，再把缺陷交给服务 owner。

这个过程展示了两个边界：测试 Agent 可以证明问题和改测试资产，但不能偷偷改业务系统让测试通过；文档声称的能力必须回到当前主分支核验，不能把待合并分支当成已上线事实。

## 成本与性能

Coding Agent 的成本常被长上下文和重复构建放大。先搜索再定点读取、先跑目标测试再跑全量、缓存不变依赖、把独立检查并行，可以减少等待。但不能为省时间跳过关键验证。

衡量时记录成功任务总耗时、模型调用、命令等待、重跑次数、人工修正、diff 大小和回滚率。生成代码速度快不代表交付快；能少走错误路径、少制造无关 diff，往往更重要。

## 方案对比

| 工作方式 | 最适合 | 优点 | 风险 |
| --- | --- | --- | --- |
| IDE 内交互 Agent | 开发者在场的小步修改 | 反馈快、上下文可控 | 容易边聊边扩大范围 |
| 独立 worktree Agent | 有边界的功能或修复 | 隔离用户改动、易审查 | 分支同步和合并成本 |
| 云端异步 Coding Agent | 明确 issue 与自动 PR | 可并行、不占本机 | 环境差异、权限与等待 |
| CI 修复 Agent | 机器可复现的门禁失败 | 证据稳定、目标明确 | 可能只优化测试表象 |

选择不取决于“哪个 Agent 更强”，而取决于任务反馈速度和所需权限。探索性设计需要人在场快速澄清；机械修复适合异步；生产事故诊断通常只读并由人控制变更。

## 实施清单

- issue 描述包含成功标准、非目标和复现信息；
- 环境准备命令可重复，不依赖个人目录；
- worktree 或分支从正确基线创建；
- 仓库规则被纳入上下文且不暴露秘密；
- 测试分为快速相关集和完整门禁；
- 长命令有超时、日志和取消能力；
- 生成文件由官方命令产生，不手工伪造；
- commit 保持逻辑单一，PR 描述给出证据；
- 失败时保留最小复现，不把脏工作树推给下一位；
- 合并后继续观察 CI 与真实运行结果。

一个实用治理指标是“无需人工重写即可合并的任务比例”，但要和改动复杂度一起看。只挑最简单 issue 会让指标虚高；应按任务类型分层，保留失败和放弃样本。

## 失败实验

在一个带未提交用户改动的仓库里放入可复现 bug。版本 A 不检查工作树直接修改和格式化全仓；版本 B 先记录状态，只改目标文件并检查最终 diff。比较无关变更、冲突和可回滚性。

再让测试依赖缺失。检查 Agent 是否把环境阻塞写成产品失败，或为了“全绿”删除测试。正确行为是保留红色证据、修复可控环境，无法继续时明确阻塞。

## 别踩这些坑

1. 在错误仓库或错误分支做正确修改；
2. 没有复现就凭报错文字猜修复；
3. 先写代码再补一个必然通过的测试；
4. 为修一行逻辑格式化整个项目；
5. 覆盖用户未提交文件；
6. 测试没跑却说“理论上没问题”；
7. 把测试仓库权限扩展成生产权限。

## 扩展阅读

代码审查 Agent 应优先指出可证明的缺陷：错误分支、并发竞态、权限扩大、资源泄露、异常吞掉和测试假绿。风格偏好只有在仓库规则明确时才应阻断。评论要带文件位置、触发条件、影响和修复方向，避免泛泛而谈“可以优化”。

Agent 生成的设计文档同样需要事实边界。描述当前能力时核对主分支，规划能力明确标记为未来；引用 issue 或 PR 时说明状态。文档漂移会让后续 Agent 从错误地图出发，造成看似合理的连锁修改。

当任务跨多个服务，先定义接口责任和验证边界，不要把所有仓库同时塞进上下文。每个服务保留独立提交和测试证据，再在集成环境验证旅程。这样失败时能知道是契约、实现还是环境问题。

对无法运行的测试如实标记环境阻塞，并给出复现命令；不要用“代码看起来正确”替代执行证据，也不要删除阻塞测试来换取绿色结果。
