# 验证与可观测性：答对一次，不叫可靠

传统函数常有清楚答案：输入 2 和 3，输出应是 5。Agent 面对的任务可能有多条可行路径，最终文字也不唯一。于是团队容易退到一句“看起来不错”。这句话适合点评朋友圈，不适合作为发布门禁。

## 先讲个故事

面试一位司机，他绕城一圈，安全抵达，你觉得很稳。第二天他遇到下雨、封路和乘客改地址，直接把车开进了婚礼现场。第一次成功证明他“曾经会开”，没有证明他能稳定处理变化。

评测 Agent 也要准备不同路况：正常任务、缺少信息、工具失败、权限不足、恶意输入、长任务和成本压力。还要知道它走了哪条路，而不只看终点那句话顺不顺耳。

## 工程上到底发生了什么

可靠性需要四层证据，它们回答不同问题：

1. **任务结果**：最终目标是否完成；
2. **执行轨迹**：是否调用了合适工具，顺序是否合理；
3. **业务证据**：外部状态是否真的改变，有没有回执；
4. **运行指标**：花了多久、多少钱、多少步，失败能否恢复。

### 先定义“成功”，再收集样本

“回答专业”太模糊。更可测的标准是：“正确识别退款资格；不执行未批准打款；生成包含订单号和原因的草稿；在权限不足时转人工。”标准应同时包含必须做到和绝不能做。

评测集要覆盖真实分布和重要边界。最有价值的回归样本常来自历史失败：一次工具选错、一次状态串台、一次超时后重复写入，都应该变成以后每次发布必跑的题。

### 不要迷信单一分数

文本相似度适合某些固定答案，却无法判断任务是否真正完成；模型裁判能评估开放文本，但也会偏好特定写法；人工复核质量高却昂贵。更稳妥的做法是组合确定性断言、业务状态检查、轨迹规则、抽样人工和模型评分。

### 可观测性不是“有一页日志”

一个可调试的运行记录应关联任务标识、模型与提示版本、工具调用、关键状态、耗时、费用、错误分类和最终证据。记录行动与观察摘要即可，不需要保存或展示模型私有思维链。敏感输入和工具结果还要脱敏、限制保留期。

### 失败分类决定下一步

产品失败要修逻辑；环境阻塞要恢复依赖；配置错误要停止执行；用户取消应保留可解释状态。如果都记成“失败”，值班同学只能从凌晨两点开始猜谜。未知状态默认不通过，叫作 fail-closed：证据不完整时，系统宁可暂停，也不自我颁奖。

> 好笑的例子：一个 Agent 的质量指标是“输出字数超过 500”。它不会退款，但能写一篇《论退款在当代消费社会中的精神意义》。指标完美，用户仍在排队。

## 别踩这些坑

1. **只测最终文本。** 工具轨迹和真实业务状态可能已经错了。
2. **用一次成功当发布证据。** 需要稳定样本、边界样本和回归。
3. **把所有失败混成一个状态。** 无法路由恢复和责任人。
4. **只看准确率。** 步数、延迟、费用和人工接管率同样影响可用性。
5. **记录越多越好。** 日志要可关联、可脱敏、有保留策略。

## 三道小测

1. 为什么“最终答案正确”仍不足以证明 Agent 安全？
2. 历史生产故障为什么应该进入评测集？
3. 缺少证据时应判 PASS、FAIL 还是 UNKNOWN/BLOCKED？

::: details 参考答案
1. 它可能调用了越权工具、重复写入或碰巧得到正确文本。  
2. 真实失败代表系统已经暴露过的风险，回归能防止同类问题复发。  
3. 应保持未知或阻塞，并且不能放行；这比假装成功更可恢复。
:::

## 本章带走

评测不是给回答打一个漂亮分数，而是建立从任务结果、执行轨迹到业务证据的完整链。可观测性让失败能被定位，回归让教训不会白交学费，fail-closed 让缺证据时系统保持诚实。
