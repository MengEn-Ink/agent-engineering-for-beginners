# 验证与可观测性：答对一次，不叫可靠

传统函数常有清楚答案：输入 2 和 3，输出应是 5。Agent 面对的任务可能有多条可行路径，最终文字也不唯一。于是团队容易退到一句“看起来不错”。这句话适合点评朋友圈，不适合作为发布门禁。

## 本章先回答什么

非确定性不等于不可测试。它意味着不能只比对一段标准答案，而要把任务成功拆成多个可观察条件，并允许存在多条合格路径。评测的目标不是消灭变化，而是区分可接受变化和真正失败。

## 先讲个故事

面试一位司机，他绕城一圈，安全抵达，你觉得很稳。第二天他遇到下雨、封路和乘客改地址，直接把车开进了婚礼现场。第一次成功证明他“曾经会开”，没有证明他能稳定处理变化。

评测 Agent 也要准备不同路况：正常任务、缺少信息、工具失败、权限不足、恶意输入、长任务和成本压力。还要知道它走了哪条路，而不只看终点那句话顺不顺耳。

## 工程上到底发生了什么

可靠性需要四层证据，它们回答不同问题：

1. **任务结果**：最终目标是否完成；
2. **执行轨迹**：是否调用了合适工具，顺序是否合理；
3. **业务证据**：外部状态是否真的改变，有没有回执；
4. **运行指标**：花了多久、多少钱、多少步，失败能否恢复。

### 先定义“成功”，再收集样本

“回答专业”太模糊。更可测的标准是：“正确识别退款资格；不执行未批准打款；生成包含订单号和原因的草稿；在权限不足时转人工。”标准应同时包含必须做到和绝不能做。

评测集要覆盖真实分布和重要边界。最有价值的回归样本常来自历史失败：一次工具选错、一次状态串台、一次超时后重复写入，都应该变成以后每次发布必跑的题。

### 不要迷信单一分数

文本相似度适合某些固定答案，却无法判断任务是否真正完成；模型裁判能评估开放文本，但也会偏好特定写法；人工复核质量高却昂贵。更稳妥的做法是组合确定性断言、业务状态检查、轨迹规则、抽样人工和模型评分。

### 可观测性不是“有一页日志”

一个可调试的运行记录应关联任务标识、模型与提示版本、工具调用、关键状态、耗时、费用、错误分类和最终证据。记录行动与观察摘要即可，不需要保存或展示模型私有思维链。敏感输入和工具结果还要脱敏、限制保留期。

### 失败分类决定下一步

产品失败要修逻辑；环境阻塞要恢复依赖；配置错误要停止执行；用户取消应保留可解释状态。如果都记成“失败”，值班同学只能从凌晨两点开始猜谜。未知状态默认不通过，叫作 fail-closed：证据不完整时，系统宁可暂停，也不自我颁奖。

> 好笑的例子：一个 Agent 的质量指标是“输出字数超过 500”。它不会退款，但能写一篇《论退款在当代消费社会中的精神意义》。指标完美，用户仍在排队。

## 设计步骤

### 第一步：写任务级成功标准

从用户结果出发，列出必须发生、不得发生和允许变化的部分。研究任务必须有可访问来源、主张与证据一致；表达方式可以不同。客服任务必须遵守政策、正确推进状态；语气可以变化。Coding 任务必须通过相关测试且不引入越权改动；代码写法可以不同。

### 第二步：建立代表性评测集

样本应覆盖常见主路径、高价值路径和风险边界。来源包括真实匿名任务、历史失败、产品规则和主动构造的极端情况。每个样本记录目标、上下文、允许工具、预期不变量、可接受结果和禁止行为，而不是只保存一段“标准回答”。

评测集需要版本。业务政策变化后，旧期望可能不再正确；模型或工具升级后，同一集合才能提供可比基线。不要在看到结果后临时改答案来“让新版本通过”。

### 第三步：优先使用确定性检查

能用代码验证的就不要先请另一个模型判断。JSON 是否符合 schema、链接是否可访问、金额是否相等、必需工具是否调用、禁止工具是否未调用、最终状态是否存在，都可以确定性断言。这类检查便宜、稳定、失败原因清楚。

### 第四步：谨慎使用模型裁判

开放文本的完整性、相关性和语气可以使用模型评分，但要有量表、示例和抽样人工校准。裁判模型可能偏好更长文本、熟悉措辞或同源模型输出。重要结论不应只依赖一个不可解释分数。

### 第五步：评估轨迹而不迷信唯一轨迹

有些任务要求工具顺序固定，例如批准前不得付款；有些任务允许先查日志或先看指标。轨迹评测应检查不变量、无效绕路和危险动作，不应因为路径与示例不完全相同就判错。可比较步骤数、重复调用、无进展轮次和人工接管是否合理。

### 第六步：连接业务状态和证据

最终文本说“已完成”不算证据。检查目标对象、状态变化、回执、版本和时间，确认结果属于本次任务。对于不可直接查询的动作，至少保存可追溯的外部标识和人工确认。

### 第七步：把线上失败变成离线回归

在线监控发现错误后，先脱敏并还原最小场景，再加入评测集。修复必须让该样本从红变绿，同时不破坏原有样本。事故复盘如果只更新说明文档，没有更新门禁，同类失败很容易换个入口回来。

## 交付型 Agent 连续案例

<CaseThread chapter="08 / 证据" title="聚合器不能替执行器写 PASS" problem="调度成功、页面可打开和报告已生成，都会制造“好像通过”的错觉。" evidence="任务结果、节点轨迹、业务回执、Run ID、时间、版本与失败分类。" />

案例门禁要求每个必需节点由实际执行器写出结果和证据。聚合器只验证集合完整性和规则，不能因为节点缺失就补一个默认 PASS。截图、日志和 JSON 都必须位于本轮目录，旧证据、路径逃逸和畸形结果直接拒绝。

这条设计把“诚实”写进系统：没执行就是没执行，环境阻塞不是产品通过，未知状态也不能被绿色页面掩盖。报告的任务不是让发布看起来顺利，而是让决策有足够事实。

## 案例与失败边界

评测常见的四个失真来源：

1. **数据泄漏**：评测样本进入提示或训练资料，系统记住答案；
2. **代理指标**：分数容易优化，却与业务成功弱相关；
3. **裁判偏差**：模型裁判偏好长度、格式或同源模型；
4. **幸存者偏差**：只统计完成任务，忽略超时、取消和阻塞。

因此报告应同时展示分母、跳过、阻塞和未知。一个“成功率 95%”若排除了最难的 40% 任务，比“成功率 80%，覆盖全部任务”更可能误导。任何豁免都应在执行前确定范围，而不是结果出来后把红灯移出统计。

## 成本与性能

成功率之外，至少跟踪每个成功任务的平均成本、p50/p95 时延、平均步骤、重复工具调用、人工接管率和失败恢复时间。按成功任务计算比按单次调用更接近业务现实：一个便宜模型若需要三次重试，可能比一次完成的较强模型更贵。

评测本身也有成本。可以采用分层策略：每次提交跑快速确定性集；每日跑代表性模型评测；发布前跑完整回归；线上持续抽样并触发人工复核。高风险场景提高抽样和门槛，低风险场景控制成本。

## 失败实验

给两个版本同一批任务：版本 A 输出更长、更像专家，但偶尔跳过工具验证；版本 B 文字简洁，却稳定检查业务状态。分别用“语言流畅度”和“任务完成 + 证据”两套指标评分，观察排名是否反转。

再把 10 个环境阻塞样本从分母中移除，比较成功率变化。这个实验能直观看到指标选择如何改变结论，也提醒团队不要在结果出来后修剪分母。

## 别踩这些坑

1. **只测最终文本。** 工具轨迹和真实业务状态可能已经错了。
2. **用一次成功当发布证据。** 需要稳定样本、边界样本和回归。
3. **把所有失败混成一个状态。** 无法路由恢复和责任人。
4. **只看准确率。** 步数、延迟、费用和人工接管率同样影响可用性。
5. **记录越多越好。** 日志要可关联、可脱敏、有保留策略。

## 三道小测

1. 为什么“最终答案正确”仍不足以证明 Agent 安全？
2. 历史生产故障为什么应该进入评测集？
3. 缺少证据时应判 PASS、FAIL 还是 UNKNOWN/BLOCKED？

::: details 参考答案
1. 它可能调用了越权工具、重复写入或碰巧得到正确文本。  
2. 真实失败代表系统已经暴露过的风险，回归能防止同类问题复发。  
3. 应保持未知或阻塞，并且不能放行；这比假装成功更可恢复。
:::

## 本章带走

评测不是给回答打一个漂亮分数，而是建立从任务结果、执行轨迹到业务证据的完整链。可观测性让失败能被定位，回归让教训不会白交学费，fail-closed 让缺证据时系统保持诚实。

## 扩展阅读

评测结果还应带置信区间和样本说明。样本很少时，不要用小数点后两位制造精确感；任务分布变化时，旧分数也不能直接代表今天。把总体指标按任务类型、风险、用户群和版本切开，才能发现平均值掩盖的退化。

最有价值的评测文化，是允许红灯存在。红灯说明系统诚实地暴露边界；为了发布而修改分母、删除难例或放宽判定，只会把问题推迟到用户现场。
