# 从 Loop 到 Graph：事情开始分叉了

最小 Agent 像一个循环：观察、行动、验证，再来一轮。可真实业务很快会出现“如果缺资料先问人”“高风险动作等待批准”“三份报告可以并行”“失败后从检查点恢复”。这时，不是再给 Prompt 加一页规则，而是把控制流画出来。

## 本章先回答什么

Graph 的价值不是让架构图更像地铁，而是让重要分支从 Prompt 的角落走到可测试、可追踪的控制面。它同样会带来版本、迁移和状态一致性问题，因此只能在复杂度真正出现时采用。

## 先讲个故事

周末你打算“去公园野餐”。简单 Loop 是：看天气 → 准备 → 出门。但朋友带了小孩、有人过敏、天气预报说下午雷阵雨，流程开始分叉：下雨转室内；孩子同行要带安全座椅；过敏者需要单独确认菜单；订不到场地则改期。

如果把所有情况写成一句话：“请灵活安排，既要又要还要，千万别出错”，负责的人只能靠临场记忆。画成状态图后，每个分支的进入条件、所需信息、失败去向和结束状态都可检查。

## 工程上到底发生了什么

Graph 不是让模型更聪明，而是让控制流更显式。节点表示一个职责清楚的步骤，边表示从一个状态转到另一个状态的条件。某些边由确定性规则选择，某些边允许模型根据上下文路由。

### 什么时候 Loop 够用

任务只有一个主目标、动作集合小、每轮都能直接判断是否完成时，Loop 最简单。例如“查资料，直到收集到三条可靠来源”。加上最大步数和失败出口就能工作。

### 什么时候需要 Graph

出现以下信号时，应考虑显式图：

- 有多个互斥分支，且每条分支的风险不同；
- 一部分任务可以并行，之后必须汇合；
- 需要暂停等待人类或外部事件，再从原处恢复；
- 不同失败要进入不同补偿路径；
- 必须证明关键节点按顺序执行，没有被模型跳过。

### 节点要小，但不能碎成沙子

节点应有单一职责和清楚输入输出，如“校验订单资格”“生成退款草稿”“等待人工批准”。如果节点叫“处理一切”，图只是把大黑箱换了个框；如果每个字段读取都拆成节点，图会变成地铁线路加毛线团。

### 持久化让暂停与恢复成为可能

执行图需要保存当前节点、图版本、关键状态和工具回执。恢复时先确认外部世界是否已变化，避免重复写入。图结构本身不会自动提供可靠性；检查点、幂等和补偿仍要单独设计。

### 不要让规则无限增生

复杂系统很容易走向“遇到一次失败就再加一条 if”。规则若没有分层、归属和删除机制，最后没人知道哪条还有效。Graph 的价值之一，是让分支成为可审阅资产：哪些是硬规则，哪些是模型路由，哪些只是临时豁免，一眼可见。

> 好笑的反例：导航系统有 382 条“如果堵车就绕路”的规则，却没有“目的地已经到了”。车很努力，乘客在终点门口绕了三圈。

## 设计步骤

### 第一步：从状态转移而不是页面步骤建模

“点击按钮、打开弹窗”是界面动作，“等待批准、执行中、已完成、需补充信息”才是业务状态。图应该围绕后者设计，避免 UI 改版就让整个流程图失效。每个状态写清进入条件、允许动作和退出条件。

### 第二步：区分硬边与软边

硬边由代码规则决定，例如金额超过阈值必须审批；软边允许模型依据上下文选择，例如优先查询日志还是指标。硬边不应被 Prompt 覆盖，软边需要记录选择依据和评测样本。图上用不同样式或元数据标记两者。

### 第三步：定义节点契约

节点契约包含输入字段、输出字段、允许工具、副作用、超时、重试、证据和错误分类。节点完成不等于函数返回；它必须写出下一节点能理解的状态。大节点难定位，小节点协调昂贵，边界应对应一个可独立验证的业务责任。

### 第四步：识别并行与汇合

互不依赖的搜索、检查或生成可以并行，但汇合节点要定义“等全部”“满足任意一个”还是“达到最低证据数量”。并行分支共享写资源时必须有冲突策略。快不是唯一目标，确定汇合语义更重要。

### 第五步：把人工等待建成正式状态

需要批准时，图进入 `waiting_for_approval`，持久化请求内容、证据、审批人、截止时间和拒绝去向。审批不是函数里卡住的一次请求，而是可能持续数小时的业务状态。恢复后还要确认请求没有过期、对象没有变化。

### 第六步：设计检查点与版本

检查点记录图版本和状态结构。发布新图时，旧运行继续旧版本、迁移到新版本，或安全终止，需要明确策略。直接用新代码解释旧状态，容易把字段含义和下一节点弄错。

### 第七步：让异常进入有限的恢复图

超时、限流、权限不足、用户取消和产品失败不应都回到“重试”。每类错误有有限路径和最大次数；补偿动作也进入图并留下证据。恢复图越清楚，主图越不需要堆满临时 if。

## 交付型 Agent 连续案例

案例图先运行静态检查，再并行执行只读健康检查和契约检查；需要写入的旅程必须先通过环境安全门。所有必需节点完成后进入聚合器。任何未知、超时或缺证据都不能汇合为 PASS。

失败诊断是另一张受限子图：它可以读日志、对比历史和生成建议，但不能修改主图结论。这样即使诊断 Agent 失败，原始执行证据仍保持完整。

## 案例与失败边界

考虑“生成并发布营销内容”的图：素材检查与数据核对可以并行；文案生成依赖两者；敏感审核与版权审核又可以并行；发布需要二者都通过并获得人类批准。下面四个问题决定图是否可靠：

1. 某个审核超时时，其他分支结果保存多久？
2. 用户修改素材后，哪些旧节点必须失效重跑？
3. 发布请求超时但实际成功，恢复时怎样避免重复发布？
4. 图版本升级后，等待中的批准还适用于新内容吗？

失败边界包括“僵尸分支”持续消耗资源、“提前汇合”忽略必需结果、“旧检查点”在新图中进入错误节点，以及补偿失败后没有独立告警。图让这些风险可见，却不会自动解决它们。

## 失败实验

设计一张包含并行搜索、人工批准和最终发布的图。故意让一个分支延迟、一个分支返回畸形状态，再让发布接口在成功后丢失回执。观察系统是否会提前汇合、永久等待或重复发布。

然后补上汇合必需集合、阶段超时、检查点和幂等查询。两轮对比的重点不是“最终都完成”，而是第一轮发生异常时能否准确停止、第二轮能否从正确状态恢复。

## 应用切片

Coding Agent 是 Graph 价值很直观的场景。一个可靠修复流程可能包含：读取任务、核对仓库状态、定位代码、写失败测试、实现修复、运行相关测试、运行全量门禁、检查差异、提交或请求审查。路径大体固定，但“定位代码”和“修复失败测试”内部需要动态探索。

如果相关测试失败，图要区分三类分支：实现错误回到修改节点；环境缺依赖进入阻塞状态；发现原需求矛盾则暂停请求人类。不能把所有失败都连回“再写一次代码”。当测试通过，仍需检查未跟踪文件和敏感信息，再进入提交节点。

研究型 Agent 的图则不同：多个子问题可以并行搜索，汇合条件不是“所有搜索都返回”，而是每个关键主张达到证据门槛。来源冲突会生成新的核验分支；预算耗尽时允许输出“部分完成 + 未确认清单”。同样是 Graph，状态和汇合语义必须由任务决定。

图还帮助运营团队读懂系统。产品可以看到哪些节点会等待人，安全可以定位写权限，值班可以找到失败分类，测试可以覆盖每条关键边。它既是运行结构，也是跨角色沟通协议。

评审一张图时，不要只沿成功路径从左看到右。反向追问每个节点：输入缺失会去哪？重复进入是否安全？运行一半升级版本怎么办？人类永远不回应怎么办？补偿本身失败怎么办？如果这些问题只能回答“理论上不会发生”，说明图只是演示流程，还没有成为生产控制面。

可以定期从历史轨迹统计最常走的边、长期不用的边和最常失败的节点。长期不用的分支可能已经过时，频繁往返的边可能表示职责划分不清。图结构也需要像代码一样被重构，而不是只增不减。

修改图之前保存代表性轨迹，用新旧版本分别回放。除了最终结果，还要比较经过的节点、调用次数、等待时间和补偿行为，防止“看起来更简洁”的新图悄悄删掉安全门。

能回放、能解释、也能回滚，才能安全演进。

## 别踩这些坑

1. **认为 Graph 自动提高智能。** 它提高的是控制流可见性和恢复能力。
2. **把每个异常都加成永久分支。** 先归类根因，临时补丁要有退出日期。
3. **节点没有输入输出契约。** 图看起来清楚，数据仍然在暗处乱流。
4. **恢复时重复副作用。** 写操作需要幂等标识和外部状态复查。
5. **全由模型选择边。** 合规、安全和金额等硬条件应由代码决定。

1. 它需要显式暂停、持久化状态、外部事件和恢复入口。  
2. Graph 是表达 Workflow 的一种方式；边可以固定，也可以动态，不等于一定是 Agent。

## 本章带走

Loop 适合单线反馈，Graph 适合显式分支、并行、等待和恢复。选择 Graph 不是为了更酷，而是为了让复杂控制流能被人看见、被测试覆盖、在失败后从正确位置继续。
