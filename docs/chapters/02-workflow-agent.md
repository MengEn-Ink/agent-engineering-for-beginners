# Prompt、Workflow、Agent，不是三种包装

很多方案把 Prompt、Workflow、Agent 画成三级火箭：Prompt 最初级，Workflow 进阶，Agent 最高级。这个比喻最大的副作用，是让团队为了“先进”而选择更难控制的系统。事实上，它们是三种不同的控制方式，没有谁天然高贵。

## 本章先回答什么

<ChapterLead :questions="['怎样判断一个任务只需要 Prompt？', 'Workflow 什么时候比 Agent 更好？', '从简单方案升级时要拿出什么证据？']" :outcomes="['一张复杂度选择梯', '一份任务不确定性清单', '一套逐级升级规则']" minutes="24" />

架构选择不是为系统贴标签，而是分配控制权。路径越固定，越应该让代码决定；环境越开放、反馈越关键，越可能需要模型在运行时做选择。正确答案常常是混合，而不是全站押注某个流行名词。

## 先讲个故事

想象你要请人准备一次十人午餐。

- 你对熟悉的厨师说：“做你最拿手的四菜一汤。”这是 Prompt：一次表达，直接得到结果。
- 你给活动公司一张流程表：确认人数 → 收集忌口 → 选套餐 → 下单 → 验收。这是 Workflow：路径由人提前规定。
- 你对助理说：“预算两千，十二点开饭，别让素食同事只吃拍黄瓜。你自己安排，遇到超预算再问我。”这是 Agent：系统根据现场信息动态决定下一步。

如果只是给八个人订固定套餐，却召集五个 Agent 开会讨论菜单，午饭可能会在晚饭时送到。架构没有输，大家都饿了。

## 工程上到底发生了什么

选择控制方式时，看三件事：路径是否稳定、环境是否变化、结果是否容易验证。

| 方式 | 谁决定下一步 | 适合什么 | 主要风险 |
| --- | --- | --- | --- |
| Prompt | 一次模型调用 | 摘要、改写、分类、提取 | 输出波动、上下文不足 |
| Workflow | 预先编写的规则 | 稳定流程、合规步骤、批处理 | 分支膨胀、规则维护 |
| Agent | 模型依据反馈动态选择 | 开放任务、工具探索、长链路交付 | 成本、漂移、难验证 |

### Prompt：把问题说清楚

Prompt 适合输入和输出边界明确的任务。比如把会议记录整理成“决定、负责人、日期”三列。只要提供结构、示例和验收标准，一次调用就可能足够。此时加入记忆、工具和循环，反而增加故障点。

### Workflow：把路径写清楚

当业务规则已知，应该让代码掌舵。例如退款必须依次完成身份校验、订单检查、额度判断和审计记录。模型可以在某个节点理解用户描述，但不能自由跳过合规步骤。Workflow 不“低级”，它把重要不变量变成了看得见的轨道。

### Agent：让下一步保持开放

当任务需要根据中间结果调整计划，Agent 才显示价值。调查一个线上故障时，系统可能先查指标，再根据异常选择日志，随后对比发布记录。路径无法预先穷举，但每次行动仍受工具权限、预算和停止条件约束。

一个好用的升级顺序是：**单次调用 → 串行 Workflow → 带路由的 Workflow → 单 Agent → 多 Agent**。每次升级都要回答：“上一层解决不了的具体问题是什么？”如果答案只是“看起来更智能”，先别升。

<DecisionLadder />

> 餐馆不会因为“自由发挥”更高级，就让厨师每天现场发明消防规范。稳定的事情写成流程，变化的事情才交给判断。

### 混合系统才是常态

真实产品常常混用三者：Workflow 固定合规骨架，Agent 在允许的节点做动态判断，普通 Prompt 完成局部提取。工程设计的目标不是选一个标签，而是把不确定性限制在真正需要它的地方。

## 设计步骤

### 第一步：给任务画“路径地图”

列出完成目标需要的主要步骤，并标记每一步是否总是发生、是否有固定前后关系、是否依赖中间结果。若大部分主路径在设计时已经知道，优先用 Workflow，把剩余开放节点交给模型，而不是把整条链都交出去。这里的“大部分”是方案判断，不是适用于所有业务的统一比例。

例如“生成周报”通常是读取数据、检查完整性、计算指标、生成解释、人工审核、发布。计算和发布顺序固定；模型适合解释变化、生成摘要。这里不需要一个能自由重排所有步骤的 Agent。

### 第二步：评估环境不确定性

不确定性来自三处：输入不完整、外部环境会变、目标有多种可接受路径。分别问：系统能通过追问补齐吗？能通过固定分支覆盖吗？必须根据工具结果临场决定吗？只有第三类持续存在时，Agent 的动态循环才有明显价值。

### 第三步：评估错误的代价与可见性

一个错误是否立刻可见、是否容易撤销，决定了可以给模型多大自由。搜索错一个网页可以重新搜；发错一封群邮件会制造真实影响；转错一笔钱更难恢复。高影响动作即使位于 Agent 流程中，也应由确定性门禁或人类批准控制。

### 第四步：建立最简单基线

先做能工作的最小版本：结构化 Prompt，或带 2–4 个节点的 Workflow。用真实样本记录成功率、人工修正、延迟和费用。只有当错误集中在“需要根据中间反馈改计划”，才升级为 Agent；若错误来自字段缺失或工具不清楚，应修输入与接口。

### 第五步：一次只升级一层

从 Prompt 到 Workflow，增加的是显式步骤；从 Workflow 到 Agent，增加的是运行时决策；从单 Agent 到多 Agent，增加的是角色和交接。一次跨两层会让改进原因无法归因。每次升级都保留上一层作对照和降级路径。

### 第六步：定义降级方案

动态系统不可用时，能否退回固定流程、生成草稿或只读模式？一个值得上线的 Agent 方案，应该明确在模型超时、工具失败、预算耗尽时，怎样让用户仍然得到部分价值，而不是整条业务链一起停摆。

## 交付型 Agent 连续案例

<CaseThread chapter="02 / 控制方式" title="质量检查应该是 Workflow 还是 Agent" problem="检查步骤有固定硬门，但排查失败原因需要根据证据动态选择。" evidence="一张控制权分配图：固定门禁由代码执行，探索性诊断由 Agent 提议并留下工具轨迹。" />

案例系统把发布检查拆成两部分。第一部分是固定 Workflow：环境、版本、权限、必需用例和证据格式依次校验，任何一项不满足就停止。第二部分是诊断 Agent：当某节点失败时，它可以搜索相关日志、对比历史运行并建议下一步，但不能修改门禁结论。

如果反过来让 Agent 自由决定“哪些检查可以跳过”，系统会把便利性放在准入规则之上。把动态分析嵌在固定骨架里，既利用模型的探索能力，又保留可审计的不变量。

## 案例与失败边界

下面四个问题能快速决定控制方式：

| 问题 | 倾向 Workflow | 倾向 Agent |
| --- | --- | --- |
| 路径能否预先写出 | 大部分可以 | 经常由中间结果决定 |
| 判断是否有硬规则 | 多且必须遵守 | 少，更多是启发式 |
| 错误能否快速验证 | 固定断言即可 | 需要继续探索环境 |
| 动作风险 | 高，顺序不可跳 | 低到中，可限制在沙箱 |

失败边界一：规则爆炸。团队看到 Workflow 分支多，就把所有判断搬进一个 Prompt。复杂性没有消失，只是从可见代码移进不可见文本。失败边界二：伪自治。Agent 每一步都必须按固定清单执行，却还承担模型调用成本；这种情况应退回 Workflow。失败边界三：过早多 Agent。一个模型尚未证明任务可行，就拆成研究、计划、执行、审核四个角色，调试面扩大四倍。

## 可复制模板

在评审会上填写这张“控制方式选择单”：

1. **目标**：最终要改变哪个业务状态？
2. **已知路径比例**：主要步骤中，有多少可以预先确定？
3. **动态反馈**：哪一步必须读到环境结果后才能决定？
4. **硬规则**：哪些条件绝不能由模型覆盖？
5. **最大损失**：一次错误最坏影响是什么，能否撤销？
6. **验证速度**：动作后多久能知道对错？
7. **简单基线**：不用 Agent 时的质量、成本和时延是多少？
8. **升级证据**：哪类失败明确证明需要更多动态性？
9. **降级模式**：模型或工具不可用时还能交付什么？

## 失败实验

挑一个原本稳定的流程，分别实现“固定 Workflow”和“自由 Agent”两个版本，用同一批 30 个样本比较：完成率、平均步骤、p95 延迟、调用费用、人工修正和无法解释的失败。再人为制造一个工具超时和一个缺失字段。

这个实验常见的结果是：固定流程在主路径上更稳，Agent 在异常探索上更灵活。真正好的设计不是选出“总冠军”，而是让二者在不同节点合作。

## 别踩这些坑

1. **认为 Prompt 越长越可靠。** 很多问题来自状态、权限、工具契约或验证，不是少写了第 87 条规则。
2. **把 Workflow 当落后方案。** 固定流程通常更便宜、可测、可审计。
3. **把所有分支都塞进一个 Prompt。** 规则一多，互相冲突且难以定位；重要不变量应落到代码或图上。
4. **为了多 Agent 而多 Agent。** 协调、交接和共享状态会制造新问题。
5. **没有升级证据。** 在基线方案没有评测数据之前，无法证明复杂架构真的更好。

## 三道小测

1. 每天按固定模板生成销售摘要，最先尝试哪种方式？
2. 退款流程中的额度校验应该交给模型自由决定吗？
3. 哪个信号说明 Workflow 可能需要升级为 Agent？

::: details 参考答案
1. 结构化 Prompt，必要时外面包一条简单 Workflow。  
2. 不应该。金额和权限属于确定性规则。  
3. 中间环境变化导致下一步无法预先穷举，并且动态选择能通过反馈验证。
:::

## 本章带走

Prompt、Workflow、Agent 是控制方式，不是段位。先用最简单、最稳定、最容易验证的方案；只有路径真的需要动态变化时，才让模型决定下一步。

## 扩展阅读

可以给架构设一份“复杂度预算”：每增加一个模型路由，就要增加对应评测；每增加一个写工具，就要增加权限和幂等设计；每增加一个 Agent，就要增加交接契约与冲突处理。预算不是为了阻止创新，而是让团队在方案评审时看见完整成本。

当简单方案达到目标，就停止升级。能用 4 个清楚节点解决的问题，不必为了画出一张漂亮的多 Agent 架构图而变成 12 个角色。克制本身就是工程能力。
